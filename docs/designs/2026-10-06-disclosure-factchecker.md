## Problem Statement

한국 상장사 분석글을 자기 이름으로 발행하는 사람(개인 투자자 겸 글쓴이, 주니어 애널리스트)은 글 속 숫자·회사·기간이 공시와 맞는지 발행 전에 직접 확인해야 한다. AI로 초안을 쓰면 그럴듯하지만 틀린 문장이 섞여 이 검수가 더 무거워진다. 틀린 숫자가 그대로 나가면 신뢰를 잃는다.

지금 저장소의 앱은 강사 원본의 메뉴 50여 개 위에 우리 기능(근거 모드·판단 일지·관심종목)이 흩어져 있어, 로그인한 사용자가 무엇을 하라는 것인지 없다(노아: "서비스 기획 관점에서 헷갈린다니까?").

## Demand Evidence

- 실사용자 0명, 매출 0원. 아래는 설립자 본인의 행동 증거뿐이다.
- 노아는 무신사 분석 때 **DART 공시와 XBRL 원자료를 직접 파싱해 매출을 원 단위(1,467,883,142,523원)까지 교차검증**했고 그 분석을 Substack에 공개했다(vault `noah-investing-philosophy`, 출처 tx-musinsa). 발행 전 검수라는 반복 작업과 품질 기준이 이미 있다.
- 공개 자료: 범용 LLM이 금융 질문에서 높은 비율로 틀린다는 보고가 반복된다(검색 결과, 수치는 출처마다 다르고 직접 검증하지 않음). 서구 도구(Fiscal.ai, AlphaSense)는 문단 단위 인용으로 대응한다.
- 증거의 한계: 다른 사람의 행동 증거가 없다. 이것이 이 설계의 가장 큰 위험이고 Assignment가 겨냥하는 지점이다.

## Status Quo

- 발행자: DART 사업보고서 PDF·뷰어에서 Ctrl+F, 엑셀에 숫자 옮겨 대조, 또는 검수를 생략하고 발행. 노아는 XBRL 직접 파싱(개발 역량이 있어서 가능한 방법).
- AI 도구: ChatGPT·Perplexity로 초안을 쓰고, 출처 링크가 있어도 그 문서가 문장을 실제로 뒷받침하는지는 사람이 다시 읽는다.
- 비용: 글 한 편당 숫자 주장 수십 개 × 공시 찾기. 시간은 측정 전이다(Assignment 1).

## Target User & Narrowest Wedge

- **가장 절박한 사람:** 한국 상장사 분석을 Substack·블로그·텔레그램에 정기적으로 발행하는 개인 글쓴이. 첫 사용자는 노아 본인. 이름을 댈 수 있는 두 번째 사용자는 아직 없다(Assignment 2).
- **가장 좁은 쐐기(wedge): 공시 팩트체커.** 적재된 회사 하나를 고르고 초안(또는 ChatGPT 답변)을 붙여 넣으면, 사실 주장 문장마다 판정·근거 공시 문단·보고서 기준일을 보여 준다. 로그인 없이 써 볼 수 있다.
- 사용자는 쓰던 AI 도구를 그대로 쓴다. 우리는 생성기가 아니라 **검수 레이어**다.

## Constraints

- 2주 안에 남에게 보여 줄 수 있어야 한다. AWS에 배포한다(노아: "우리가 일단 AWS로 배포하기는 할건데").
- 판정은 TypeSafe JEV(유료 외부 API). 공개 문서에 TypeSafe 가격·금액을 쓰지 않는다. 비용은 파이프라인 전체를 대형 모델 대비 상대 비율로만 보인다(노아 결정).
- 사전등록 원칙과 이미 연 확인 세트·홀드아웃을 다시 쓰지 않는 규칙은 그대로다.
- 알려진 약점: 주어가 바뀐 문장(다른 부문·제품 이름)을 잘 못 거른다(A-3·A-4 미통과, 공개). ✅는 "발행해도 된다"는 승인이 아니다.
- **근거 원천의 한계(코드 확인):** 적재 문단은 사업보고서 'I. 회사의 개요'와 'II. 사업의 내용'(안의 표 포함, 표 단위 반영)뿐이다. 'III. 재무에 관한 사항'(재무제표)과 XBRL 수치는 색인에 없고, 연결/별도 구분 메타데이터도 없다. 재무제표에만 있는 숫자 주장은 ❔가 될 수 있다.
- 적재 범위: 시드 15개사(삼성전자·SK하이닉스·NAVER·카카오·현대자동차·기아·현대모비스·LG화학·삼성SDI·LG에너지솔루션·POSCO홀딩스·셀트리온·삼성바이오로직스·SK·SK이노베이션)와 평가용 회사 일부. 무신사는 없다.

## Premises

AI 리드가 정했다(노아 위임). 각 전제에 뒤집는 증거를 적었다.

1. 서비스의 첫 가치는 "AI 답변 생성"이 아니라 "이미 있는 글의 공시 검수"다. — 관측 방법: 입력 칸에 출처 선택(내 초안 / AI 답변 / 남의 글)을 두고, 사용자 인터뷰에서 "검수 도구와 질문 도구 중 무엇이 먼저 필요한가"를 묻는다. 뒤집는 증거: 인터뷰 다수가 질문 도구를 원하고, 붙여넣기 사용이 첫 1회 뒤 끊긴다.
2. **가설(출처: Codex 독립 의견, 사용자 행동 증거 아님):** 서비스 사용자는 추론 비용보다 검수 시간·오류 위험 때문에 쓴다. 그래서 사용자용 문구는 "발행 전 검수 시간 단축·틀린 숫자 차단"이고, "작은 모델+판단 모델의 비용 효율"은 채용 담당자용 공개 페이지의 메시지다(노아가 고른 비용 효율 메시지는 층을 나눠 유지). — 뒤집는 증거: 발행자가 비용 설명 없이는 재사용하지 않거나, 유료 전환 논의에서 비용이 먼저 나온다.
3. 붙여넣기 검수에는 답변 생성(8B LLM)이 필요 없다. 문장 분리(코드 `claims.claim_spans`)·문단 검색(임베딩)·숫자 대조(코드 `numbers.py`)·판정(JEV)만 쓴다. 그래서 **AWS에 GPU 없이** 올린다. 채팅형 근거 모드는 배포판에서 **끈다**(미리 계산한 예시 화면도 만들지 않는다. '어떻게 검증하나' 페이지에는 로컬 스크린샷만).
4. 강사 원본 메뉴와 **원본 API 라우트**는 배포판에서 끈다. UI만 숨기지 않고, 배포 프로필에서 허용 목록에 있는 라우터만 등록한다(아래 Recommended Approach의 공개 엔드포인트 목록). 코드는 지우지 않는다(출처 보존).
5. 판단 일지·관심종목은 버리지 않지만 **배포판에서 숨긴다**(로그인 후에도). 외부 발행자의 재사용 신호가 나온 뒤에 "검수 결과로 판단 기록 남기기"로 연결한다.

## Cross-Model Perspective

Codex(다른 계열 모델) 독립 의견, 요약:

- 가장 강한 제품: 한국 기업 분석글을 발행하기 직전에 쓰는 공시 대조 도구. 첫 고객은 자기 이름으로 발행하는 사람.
- 결정적 사실: "발행 전에 DART/XBRL을 직접 파싱해 원 단위까지 교차검증한다" — 이미 반복하는 작업과 품질 기준이 있다.
- 틀린 전제: "비용 효율"이 대표 메시지라는 것(→ Premise 2를 가설로 반영).
- 48시간 제품: 화면 두 개(입력·결과). 초록 배지를 발행 승인처럼 보이지 않게. 채팅·관심종목·일지·결제·모델 대결은 첫 화면에서 뺀다(→ Premise 3·5에 반영).
- 채용 데모: 실제 초안을 도구로 검수하는 과정. AI 리드 수정: "도구가 발행 가능한 글로 만든다"가 아니라 **"작성자가 도구의 표시를 보고 직접 확인·수정한 과정"**으로 보인다. 발행 판단은 사람이 한다. 엔진이 놓친 주어 바꿔치기 사례도 함께 공개한다.

## Approaches Considered

### Approach A: 공시 팩트체커 단독(최소)
- 붙여넣기 → 문장별 판정 화면 두 개. 기존 판정 엔진·문단 검색·숫자 대조·배지 화면 재사용. 배포판에서 원본 메뉴·라우트 끔.
- 노력 M(사람 2주 / AI 4~5일, AWS 첫 배포 포함). 위험 중간(배포·벡터 이전).

### Approach B: 리서치 노트 전체 흐름(이상형) — 지금은 하지 않음
- 생성기 때문에 AWS에 GPU 또는 유료 LLM API가 필요하고, 첫 사용자에게 할 일이 여럿이라 쐐기가 흐려진다.

### Approach C: 공유 가능한 검수 리포트(측면)
- A의 결과를 고정 링크로 만들어 발행자가 글에 붙인다. 독자가 문장별 근거를 본다. 성장 고리이자 채용 데모 링크.

## Recommended Approach

**1주차 A, 2주차 C. B·A-5·일지 연결은 2주 범위 밖.**

### 첫 사용 흐름
1. 랜딩(로그인 없이): "분석글을 붙여 넣으면 문장마다 DART 공시와 대조합니다. ✅는 검색된 공시 문단과 일치한다는 뜻이고, 사실 보증·발행 승인이 아닙니다."
2. 회사 선택: **적재된 회사만** 목록에 나온다. 검색에서 못 찾으면 "아직 적재되지 않은 회사 — 요청하기"(요청 수만 센다, 자동 적재 없음).
3. 출처 선택(내 초안 / AI 답변 / 남의 글) + 붙여넣기(익명 최대 2,000자·30문장).
4. 결과: 문장마다 아래 배지, 근거 문단(펼치기), 보고서명·사업연도·접수번호. 상단에 "적재된 최신 보고서: ○○○○년 사업보고서(접수일)"과 알려진 약점 상시 표시.
5. (선택) 로그인 → 결과 저장·공유 링크(2주차). 익명 결과는 서버에 남기지 않으므로 로그인 뒤에 이어 붙이지 않는다. 로그인 후 다시 검수하면 그 회차는 사용자 한도에서 센다.

### 처리 흐름: 1단계 검수 대상 분류 → 2단계 공시 대조(노아 제안)

노아 제안: "초안을 넣으면 1단계로 JEV가 문장 단위로 검수가 필요한 문장인지 일반 문장인지 나누고, 검수가 필요하다고 확인되면 우리 방식대로 공시와 비교해 팩트체크." 팩트체크 분야의 검수 가치 판별(check-worthiness)과 같은 구조이고, JEV(선택지를 고르는 판단 모델)에 맞는 일이다.

1. **문장 분리**(코드 `claims.claim_spans`).
2. **1단계 분류.** 범주: 공시로 확인할 사실 / 의견·전망 / 공시 범위 밖(주가·목표주가·추정치·시장 전망) / 다른 회사가 주어.
   - **규칙 먼저:** 숫자·회사명·기간 표현이 든 문장은 규칙으로 검수 대상에 넣는다(JEV 분류를 거치지 않음). 놓치면 안 되는 문장이 분류 오류로 빠지지 않게 하는 장치다.
   - **나머지는 JEV:** 초안의 나머지 문장을 한 번의 JEV 요청(문장마다 선택형 질문 하나, A-4의 묶음 방식)으로 분류한다.
   - **애매하면 검수:** '검수 안 함' 범주 확률이 높을 때만 건너뛴다. 기준값은 조정 세트에서 정한다(재현율 우선).
   - 건너뛴 문장도 회색으로 이유를 붙여 보여 주고, 사용자가 눌러 검수를 요청할 수 있다.
3. **2단계 공시 대조.** 검수 대상 문장만 기존 방식(문단 검색 → 숫자 대조 → JEV 판정)으로 판정한다.
4. **3단계 결과 표시 — LLM 없이 코드로.** 판정 결과를 LLM이 다시 요약하면 확인되지 않은 표현이 새로 섞일 수 있으므로 생성 모델을 쓰지 않는다. 상단 요약(✅·⚠️·❔·건너뜀 개수, 코드가 셈), 원문 문장 목록(⚠️·❔ 먼저), 펼치면 근거 문단·보고서명·기준일, 숫자가 어긋나면 문단 속 공시 숫자(`numbers.py`로 추출)를 나란히 보인다. GPU 없는 배포 전제도 유지된다.
   - **수정 제안(LLM)은 2주 범위 밖.** 붙일 때는 제안 문장을 다시 2단계로 검수해 ✅인 것만 보인다.

### 판정 범주(엔진 출력과 대응, 코드 확인)
| 엔진 상태 | 배지 | 문구 |
|---|---|---|
| `supported` | ✅ | 검색된 공시 문단과 일치 |
| `contradicted` | ⚠️ | 공시와 어긋날 수 있음 — 직접 확인 필요(⚠️ 정확도는 사전등록 평가에서 따로 검증하지 않았다. 아래 Success Criteria에서 측정) |
| `no_evidence` | ❔ | 적재된 공시에서 못 찾음 |
| `unjudged` | ⊘ | 판정 불가(오류·한도) |
| 주장 아님(`claims.is_not_claim`) | 회색 | 의견·전망 — 검수 안 함(개수에서 뺌) |
| 범위 밖 | 회색 | 다른 회사가 주어(상장사 사전·회사명 규칙으로 감지) 또는 적재 보고서와 다른 연도·분기를 명시 — 검수 안 함 |

### 숫자 범위(1차)
- 공시 문단에 그대로 있는 값만 대조한다. 단위 환산(조·억·백만)과 반올림·버림 일치는 `numbers.py`가 이미 한다.

> Constraints는 근거 원천이 최신 사업보고서의 I·II절뿐이고 III절(재무제표)·XBRL이 색인에 없어 재무 숫자 주장이 ❔가 될 수 있다고 적는다. 그런데 랜딩 문구는 '문장마다 DART 공시와 대조합니다'이고, 결과 화면에서 상시 표시하는 '알려진 약점'은 Constraints에서 주어 바꿔치기와 따로 적혀 있어 이 원천 한계가 포함되는지 알 수 없다. 분석글의 매출·영업이익 같은 핵심 숫자가 ❔로 찍히면 사용자는 '공시에 없다'로 읽을 수 있다(R1-9의 '화면에 반영' 의무가 남음).

**Remedy**

> 랜딩과 결과 상단에 '검색 범위: 최신 사업보고서 I·II절(재무제표·XBRL 제외)'을 명시하고, ❔ 문구를 '검색 범위 안에서 못 찾음'처럼 원천 한계를 드러내게 고친다.

### R2-2 — clarity

**Problem**

> 숫자 범위는 증감률·이익률 같은 파생 지표를 1차 범위 밖으로 두면서 표시를 '❔ 또는 범위 밖'으로 열어 두었다. 또 파생 지표 문장을 무엇으로 감지하는지(numbers.py가 % 값을 구분하는지, 별도 규칙인지)가 없어, 'YoY 18% 증가' 같은 맞는 문장이 엔진에 들어가 ⚠️로 나올 수 있다(R1-10의 '파생 지표 처리 결정' 의무가 남음).

**Remedy**

> 파생 지표 문장의 배지를 하나로 정하고(권장: 범위 밖 회색, 판정 호출 안 함), 감지 규칙(퍼센트·증감 표현 등)과 그 위치(numbers.py 확장 / 범위 밖 분류기)를 적는다.

### R2-3 — clarity

**Problem**

> 기간 규칙은 '적재 보고서와 다른 연도·분기를 명시'한 문장을 범위 밖으로 둔다. '작년', '올해', '전년 대비', '최근 분기' 같은 상대 표현의 처리, II절 표에 함께 실린 과거 연도 값(다년 추이)이 있는 문장의 처리가 정해지지 않았다. 또 10월 시점 초안의 최근 분기 실적 문장은 모두 회색이 되는데, 쐐기 가치(발행 직전 검수)에 미치는 영향이 첫 사용 흐름·성공 기준에 반영되지 않았다.

**Remedy**

> 상대 기간 표현을 보고서 사업연도로 해석하는 규칙과, 적재 보고서 안에 있는 과거 연도 값을 범위 안으로 둘지를 정한다. 범위 밖 회색 비율을 기준선·도그푸드에서 함께 기록하도록 성공 기준에 넣는다.

### R2-4 — feasibility

**Problem**

> 판정 범주 표는 '엔진 출력과 대응, 코드 확인'이라고 하지만 '범위 밖'(다른 회사 주어·다른 기간)은 엔진 출력이 아니라 새로 만들 분류기다. 회사 감지에 쓸 '상장사 사전'의 원천(OpenDART 고유번호 목록 등)·갱신, 자회사·계열사 이름 처리, 구현 위치가 없고 Approach A 노력 추정(AI 4~5일)에도 들어 있지 않다.

**Remedy**

> 범위 밖 분류기를 신규 구성요소로 표에서 구분하고, 회사명 사전의 원천과 적재·갱신 방법, 판정 파이프라인에서의 위치(JEV 호출 전 필터)를 적은 뒤 노력 추정에 포함한다.

### R2-5 — consistency

**Problem**

> 도그푸드 지표는 '변조 문장이 ✅가 아닌 비율'을 탐지로 센다. 그런데 제품은 다른 연도를 적은 문장과 다른 회사가 주어인 문장을 '범위 밖(검수 안 함)' 회색으로 돌린다. 기간 변조와 고객사 이름 바꿔치기 변조는 엔진 판정 없이 회색이 되어 '탐지'로 집계될 수 있고, 사용자 화면에서는 오류 표시가 아니라 '검수 안 함'이다. 반대로 지지 원문이 회색·⊘가 되면 오경보로 셀지도 정해지지 않았다.

**Remedy**

> 지표 정의에서 회색(주장 아님·범위 밖)과 ⊘를 탐지·오경보에 어떻게 넣을지(별도 칸으로 보고, 탐지는 ⚠️·❔만 인정 등)를 사전등록 전에 정한다. 기간·주어 변조는 범위 밖 분류기와 엔진 결과를 나눠 보고한다.

### R2-6 — scope

**Problem**

> 증권사 리포트 변조 도그푸드(리포트 수집, Opus·Codex 라벨 두 벌과 불일치 2차, 5유형 변조, 조정·확인 세트 사전등록과 1회 판정)가 1~2주차에 들어 있다. 이는 A-5를 범위 밖으로 뺀 것과 같은 크기의 별도 작업인데 Approach A 노력 추정에 없고, 2주 일정이 밀릴 때 A·C·도그푸드 중 무엇을 먼저 미룰지도 없다.

**Remedy**

> 도그푸드의 노력 추정과 2주 안 우선순위(예: 배포·안전장치 > 도그푸드 조정 세트 > 확인 세트 판정 > 공유 링크)를 적거나, 확인 세트 판정을 2주 범위 밖으로 미룬다.

### R2-7 — completeness

**Problem**

> 도그푸드의 원문 라벨은 AI(Opus·Codex)가 만든 참조 라벨인데, 공개 계획('어떻게 검증하나' 페이지·채용 데모의 탐지율·오경보율)에는 라벨이 AI가 만든 것이라는 고지가 없다. 프로젝트 규칙은 AI가 만든 라벨을 그렇게 밝히도록 한다.

**Remedy**

> 공개 항목에 '정답 라벨은 AI 두 모델이 만들고 불일치만 재검토했다(사람 검수 범위: …)'를 넣는다고 적는다.

### R2-8 — feasibility

**Problem**

> 유형별 탐지율·오경보율을 공개한다고 하지만 리포트 수, 유형별 변조 문장 수, 확인 세트 최소 표본이 없다. 리포트 문장 상당수가 목표주가·추정치·분기 실적이라 '확인 가능한 문장'이 적을 수 있어, 유형별 비율이 몇 개 표본에 기대게 될 수 있다.

**Remedy**

> 유형별 최소 표본 수(또는 신뢰구간 보고)를 사전등록 항목에 넣고, 표본이 모자라면 유형을 합쳐 보고하는 규칙을 정한다.

### R2-9 — completeness

**Problem**

> 성공 기준 '5명 중 2명 이상이 다음 글에서 다시 쓴다'와 Premise 1의 반증 신호 '붙여넣기 사용이 첫 1회 뒤 끊긴다'는 같은 사용자의 재사용을 식별해야 관측된다. 그런데 익명 원문·결과는 저장하지 않고, 사용 이벤트 기록(회차·출처 선택 집계·사용자 식별)도 정의되지 않았다.

**Remedy**

> 측정용 이벤트(검수 실행 시각, 출처 선택, 판정 개수, 로그인 사용자 ID 또는 익명 세션 해시)를 원문 없이 남기는 방식과, 모집한 발행자 5명은 로그인으로 쓰게 하거나 인터뷰로 확인하는 방법을 정한다.

### R2-10 — consistency

**Problem**

> 갱신 주기는 '분기 1회 수동'인데, 적재 대상과 검색 범위는 '적재된 최신 사업보고서 1건'(연 1회 제출)이다. 분기보고서를 적재하는지, 분기 갱신이 무엇을 바꾸는지 서로 맞지 않는다.

**Remedy**

> 적재 대상이 사업보고서뿐이면 갱신을 '사업보고서 제출 시기(3~4월) 1회 + 신규 회사 추가 시'로 고친다. 분기보고서도 적재한다면 보고서 선택 규칙과 기간 범위 밖 규칙을 그에 맞게 고친다.

### R2-11 — consistency

**Problem**

> 안전장치는 '서버 전체 하루 JEV 입력 토큰 상한(기존 전체 한도 재사용)'을 공개 전 필수로 확정하지만, 배포 절은 '비용 상한은 노아 확인 뒤'라고 한다. 상한 값이 이미 정해졌는지, 공개 전 노아가 정할 항목인지 알 수 없다.

**Remedy**

> '기존 전체 한도 변수를 재사용하되 공개용 값은 노아가 공개 전에 정한다'처럼 결정 주체와 시점을 한 문장으로 맞춘다.

### R2-12 — completeness

**Problem**

> 익명 한도 'IP·세션당 하루 3회'는 IP와 세션 중 하나만 넘어도 막는지(둘 다 기준인지) 정해지지 않았고, 세션은 쿠키 삭제로 쉽게 초기화된다. 카운터 저장소도 없는데 배포 절은 Redis를 뺄 수 있다고 한다.

**Remedy**

> 익명 한도 키(IP 기준 필수, 세션은 보조 등)와 카운터 저장소(PostgreSQL 표 / Redis 유지)를 정한다. IP를 저장한다면 해시·보존 기간을 개인정보 항목에 함께 적는다.

### R2-13 — completeness

**Problem**

> 로그인 사용자 결과 저장이 1주차인지 2주차인지('(선택) 로그인 → 결과 저장·공유 링크(2주차)') 모호하고, 저장 결과에 초안 원문이 들어가는지, 보존 기간, 사용자가 지울 때 공유 링크도 함께 지워지는지가 정해지지 않았다. 1주차에 로그인이 사용자에게 주는 것이 한도 확대뿐인지도 불분명하다.

**Remedy**

> 결과 저장의 주차, 저장 항목(원문 포함 여부), 보존 기간, 삭제 시 공유 링크 연쇄 철회를 적는다. 1주차 로그인의 용도를 명시한다.

### R2-14 — completeness

**Problem**

> 공개 엔드포인트 허용 목록은 1주차 배포 절에만 있고 2주차 공유 리포트에 필요한 라우트(결과 저장, 공유 링크 생성·철회·삭제, 토큰 링크 공개 조회)가 없다. 허용 목록 방식에서는 이 라우트를 명시적으로 추가해야 열린다.

**Remedy**

> 2주차 허용 목록 추가분과 각 라우트의 인증 요구(공개 조회만 익명, 나머지 로그인)를 적는다.

### R2-15 — completeness

**Problem**

> 출처 선택에 '남의 글'이 있고, 2주차 공유 리포트는 판정된 문장·배지를 공개 링크로 보여 준다. 다른 사람의 글 문장을 재게시하고 ⚠️ '공시와 어긋날 수 있음'을 공개 표시하면 저작권·명예 관련 위험이 생긴다. 이 조합의 허용 여부가 정의되지 않았다.

**Remedy**

> 출처가 '남의 글'인 결과는 공유 링크를 막거나, 문장 원문 없이 집계만 공유하도록 정한다. 공유 시 작성자 본인 글임을 확인하는 문구를 둔다.

### R2-16 — clarity

**Problem**

> 익명 입력 상한(2,000자·30문장)을 넘을 때 거부하는지 앞부분만 자르는지, 30문장이 전체 문장 수인지 '주장 아님'을 뺀 판정 대상 수인지가 정해지지 않았다. 한도 회차·JEV 호출 수 계산이 이 정의에 달려 있다.

**Remedy**

> 초과 입력의 동작(입력 단계에서 거부·안내 권장)과 상한의 집계 대상(판정 대상 문장 기준 등)을 적는다.

### R2-17 — feasibility

**Problem**

> 지연 목표는 문장들을 병렬 판정하고 '문장별로 끝나는 대로 표시'한다고 하지만, 점진 표시 전달 방식(SSE·폴링 등)과 요청당·서버 전체 동시 JEV 호출 수 상한이 없다. 여러 익명 사용자가 동시에 30문장씩 넣으면 외부 API 속도 제한·지연 목표와 충돌할 수 있다.

**Remedy**

> 점진 표시 방식과 동시 호출 상한(요청당 N, 서버 전체 M), 초과 시 대기열 또는 ⊘ 처리를 정한다.

### R2-18 — feasibility

**Problem**

> 벡터 이전은 Qdrant `evidence_passages` 스냅샷만 다룬다. 결과 화면과 회사 선택에 필요한 적재 회사 목록, 보고서명·사업연도·접수번호·접수일 메타데이터, 판정 근거 문단 조회가 Qdrant 페이로드만으로 되는지, PostgreSQL 근거 표(마이그레이션)도 옮겨야 하는지 적혀 있지 않다.

**Remedy**

> 이 데이터들의 원천(Qdrant 페이로드 / PostgreSQL 표)을 확인해 적고, PostgreSQL 쪽이 필요하면 덤프·마이그레이션 절차를 배포 절에 넣는다.

### R2-19 — clarity

**Problem**

> Assignment 1은 무신사를 '상장 직후'라고 단정하지만 출처가 없다. 문서의 다른 사실 주장과 달리 근거·미검증 표시가 없다.

**Remedy**

> 출처를 붙이거나 '상장 여부·사업보고서 유무 미검증'으로 고친다. 결론(시드 회사 사용)은 '시드에 없다'만으로 충분하다.

### Prior finding evidence

**R1-9 → R2-1 (persisting)**

> Constraints와 숫자 범위 절이 근거 원천(I·II절만, III절·XBRL 제외, 연결/별도 메타 없음)을 정했지만, 원래 의무 중 '이 한계를 화면에 반영'은 남았다. 랜딩은 'DART 공시와 대조'라고만 하고 결과 상단의 상시 표시가 원천 한계를 포함하는지 적혀 있지 않다.

**R1-10 → R2-2 (persisting)**

> 단위 환산·반올림은 numbers.py로 정했으나, 파생 지표 처리는 '❔ 또는 범위 밖으로 표시'로 둘 중 하나를 고르지 않았고 감지 방법도 없다.

## Step 0: Scope Challenge

- **이미 있는 것(재사용):** 문장 분리 `evidence/claims.claim_spans`·`is_not_claim`, 숫자 대조 `evidence/numbers.py`(단위 환산·반올림·표 단위), 판정 `evidence/judge.py`(문단 8개 묶음 JEV 1회, `supported/contradicted/no_evidence/unjudged`), JEV 클라이언트 `app/lib/jev.py`(키 파일·토큰 상한), 문단 분해 `evidence/passages.py`, DART 클라이언트 `evidence/dart.py`(`list.json`·`document.xml`·`corpCode.xml`), Qdrant 저장소 `evidence/store.py`, 일일 한도 설정 `EVIDENCE_DAILY_*`, 폴링형 실행 화면 패턴(`/api/evidence/runs/{id}`).
- **없는 것(새로):** 다문서·전체 절 수집과 기간 메타데이터, XBRL 재무 수치(OpenDART `fnlttSinglAcntAll`, 저장소 미사용), 1단계 검수 대상 분류, 범위 밖 판별(다른 회사·기간·파생 지표), 익명 한도, 팩트체커 화면, 배포 프로필.
- **핵심 구조 결정(D1, AI 리드 자동 결정):** 새 코드는 `app/services/factcheck/`에 두고 **`app/services/evidence/*.py`는 고치지 않는다.** 그 폴더는 A-2~A-4 사전등록의 `code_sha256` 대상이라 고치면 동결 대조가 깨진다(재현은 동결 커밋에서 가능하지만 불필요한 소음). 재사용은 import로만 한다. 새 Qdrant 컬렉션 `factcheck_passages`를 써서 근거 모드의 `evidence_passages`와 섞지 않는다.
- **화면 결정(D2):** 원본 `app.html`(메뉴 50여 개)을 고치지 않고 **새 독립 페이지 `public/factcheck.html` + `public/js/factcheck.js`**를 만든다. 배포 프로필에서 루트(`/`)가 이 페이지를 연다. 원본 메뉴 '숨김' 작업이 통째로 사라진다(가장 작은 변경).
- **복잡도:** 새 파일 약 12~16개(서비스 6, 라우트 1, 마이그레이션 1, 페이지 2, compose·문서 2, 테스트 4~5), 새 서비스 성격 구성요소 4개(수집기·분류기·XBRL 대조기·파이프라인). 8파일·2서비스 기준을 넘지만, 기능 목록은 이미 설계에서 승인됐고 더 작은 배치는 없다(각 구성요소가 하나의 책임). → **scope accepted as-is**, 배치는 위 D1·D2로 오히려 원본 수정이 줄었다.

## 1. Architecture

```
[factcheck.html] --POST /api/factcheck {corp_code, text, source}--> [routes/factcheck.py]
     ^                                                                  | 한도 확인(익명: IP 해시, 로그인: 사용자)
     |  GET /api/factcheck/{job_id} (폴링, 문장별 결과 누적)               v
     +-------------------------------------------------------- [job store: 메모리, TTL 15분, 원문 미저장 영속]
                                                                        |
                       factcheck/pipeline.check(corp_code, text) -------+
                         |
   0 문장 분리 ── evidence.claims.claim_spans
   1 분류 ─────── factcheck/triage: 규칙(숫자·회사명·기간 → 검수) → 나머지 JEV 묶음 분류 1회
                  factcheck/scope:  다른 회사(상장사 사전) / 기간 해석 / 파생 지표 → 범위 밖
   2 대조 ─────── 기간 → 후보 문서(payload 필터 period·report_type) → Qdrant 검색 8개
                  ├─ 재무 계정 주장: factcheck/xbrl 코드 대조(연결/별도·기간·계정) ── 일치/불일치/모름
                  └─ evidence.numbers 숫자 확인 → evidence.judge JEV 판정
   3 표시 ─────── 배지·근거 문단·보고서명·기간·XBRL 값(코드), LLM 없음
```

- **D3 기간 매칭:** 문장에서 연도·분기·반기를 뽑고(정규식), 상대 표현('작년·올해·전년 대비·최근 분기')은 **검수 실행일 기준이 아니라 사용자가 고른 '기준 시점'(기본: 적재된 가장 최근 보고서 기간)**으로 해석한다. 해석 못 하면 '기간 불명'으로 최근 정기보고서·잠정실적 전체를 검색 범위로 둔다. (R2-3 해결 방향)
- **D4 XBRL 대조 우선:** 매출액·영업이익·당기순이익·자산·부채·자본 등 계정 사전에 걸리는 숫자 주장은 XBRL 값과 코드로 먼저 대조한다. 불일치면 ⚠️(근거: XBRL 계정·기간·연결/별도), 일치면 ✅ 근거로 쓴다. 연결/별도가 문장에 없으면 연결 우선, 별도로 일치하면 그 사실을 표시한다. 계정 사전 밖이면 기존 문단 판정으로 간다.
- **D5 파생 지표:** 증감률·이익률·YoY·비중(%) 문장은 **XBRL 두 값으로 계산 가능한 것(증감률·영업이익률)만 코드로 계산해 대조**하고, 그 밖은 '범위 밖(파생 지표)' 회색. 배지를 하나로 정함(R2-2).
- **D6 다른 회사:** OpenDART 고유번호 목록(`fetch_corp_codes`, 상장사)에서 회사명 사전을 만들고, 문장 주어 자리(문장 앞부분)에 선택 회사가 아닌 상장사명이 오면 '범위 밖(다른 회사)'. 자회사명은 사업보고서 '계열회사 현황' 절에서 뽑아 같은 회사로 본다. (R2-4)
- **D7 상태 저장:** 익명 결과는 **프로세스 메모리 job store(TTL 15분)**에만 두고 DB·로그에 원문을 남기지 않는다. `# ponytail: 단일 인스턴스 메모리 저장, 다중 인스턴스면 Redis로`. 로그인 사용자의 결과 저장·공유는 2주차(R2-13: 1주차 로그인 용도 = 한도 확대만).
- **D8 한도(R2-11·12·16):** 익명 키 = `sha256(IP + 일별 솔트)`(원 IP 미저장, 하루 지나 솔트 교체로 연결 불가), 하루 3회, 1회 판정 대상 30문장(초과 입력은 입력 단계에서 거부·안내, 2,000자). 로그인 사용자 = 기존 `EVIDENCE_DAILY_USER_*`. 서버 전체 = 기존 `EVIDENCE_DAILY_GLOBAL_TOKENS` 변수 재사용, **공개용 값은 노아가 공개 전에 정한다**. 카운터는 PostgreSQL 표 `factcheck_quota(key, day, count)`(마이그레이션 1개, Redis 불필요).
- **D9 동시성(R2-17):** 요청당 JEV 동시 4, 서버 전체 동시 8(asyncio 세마포어). 넘으면 대기, 30초 넘으면 남은 문장 ⊘(판정 불가: 혼잡). 점진 표시는 기존 폴링 패턴(1초 간격).
- **D10 배포 데이터(R2-18):** 서버에 필요한 데이터 = Qdrant `factcheck_passages` 스냅샷(문단 + payload: corp_code·rcept_no·report_type·report_nm·period·rcept_dt·section·idx·text) + `xbrl_facts.json`(계정 값) + 상장사명 사전 JSON. PostgreSQL은 빈 DB에 마이그레이션만(근거 모드 표 불필요). 갱신 = 정기보고서·잠정실적 공시 때 로컬 수집 → 스냅샷·JSON 재업로드(R2-10: 분기 1회가 맞다 — 이제 분기보고서·잠정실적을 적재하므로).
- **D11 배포 프로필:** `APP_PROFILE=factcheck`이면 `main.py`가 허용 라우터만 등록(auth·factcheck·health·정적 파일). 원본 라우터는 등록 안 함(R1-14 유지). 2주차 공유 라우트(R2-14)는 그때 허용 목록에 추가: 공유 생성·철회(로그인), 토큰 조회(익명).
- **D12 표시 문구(R2-1):** 랜딩·결과 상단에 "검색 범위: 삼성전자·SK하이닉스 최근 3년 정기보고서·잠정실적·주요사항보고서·XBRL 재무 수치"와 알려진 약점(주어 바꿔치기)을 상시 표시. ❔ 문구 = "검색 범위 안에서 못 찾음".
- **D13 '남의 글'(R2-15):** 출처가 '남의 글'이면 2주차 공유 링크를 막는다(본인 글만 공유). 1주차에는 공유가 없어 영향 없음.
- **실패 모드(새 경로마다):** JEV 시간 초과 → 해당 문장 ⊘(보임), Qdrant 다운 → 전체 실패 메시지(보임), XBRL 데이터 누락 연도 → 문단 판정으로 대체(보임: 근거 종류 표시), 1단계 JEV 실패 → **전 문장 검수로 대체**(놓침 방지, 비용↑ 기록), 한도 소진 → 안내(보임). 조용한 실패 없음 → critical gap 0.
