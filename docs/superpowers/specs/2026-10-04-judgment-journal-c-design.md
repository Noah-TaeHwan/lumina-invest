## 1. 목적과 범위

README 목표 축 "자료 확인 → AI 설명 → 판단 기록"의 마지막 칸을 만든다. A-1·A-2가 앞 두 칸(공시 문단 검색, 문장마다 근거 판정이 붙은 AI 답변)을 만들었다. 모듈 C는 사용자가 그 답변을 보고 **자기 판단을 기록**하고, 나중에 **당시 근거와 판정을 그대로 다시 보며** 그 사이 공시가 바뀌었는지 확인하게 한다.

일지가 지키는 원칙 세 가지:

1. **당시 화면을 보존한다.** 판정 정책·문단·대화가 나중에 바뀌거나 지워져도, 사용자가 판단할 때 본 답변·배지·근거 문단을 그대로 다시 보여 준다.
2. **판정을 사실 보증처럼 보이게 하지 않는다.** A-2 결과에서 ✅ 정밀도 목표는 확인되지 않았고(0.903, 관문 실패), 주체 교체 문장의 정확도는 0.57이었다(`evidence-a2-interpretation.md:13,23`). 일지는 배지를 "검색된 공시 문단 기준 AI 판정"으로만 보여 주고, 배지에서 판단을 추천하거나 점수를 내지 않는다.
3. **판단은 사용자가 쓴 것이다.** 메모는 밖으로 나가지 않는다(외부 판정·LLM·알림 어디에도 보내지 않는다).

## 3. 사용자 시나리오와 화면 상태

### 결정 3-1. 일지는 판정 실행 하나에서만 시작한다

- **추천:** 판단 기록은 근거 모드 답변의 **종결된 판정 실행 하나**에서만 만든다. 답변 요약줄 옆에 `판단 기록` 버튼을 두고, 누르면 그 실행을 기준으로 기록 양식이 열린다. 빈 일지(회사만 고르고 메모 쓰기)는 만들지 않는다.
- **근거:**
  - 목표 축이 "자료 확인 → AI 설명 → 판단 기록"이다. 판단이 어떤 근거를 보고 내려졌는지가 일지의 핵심 가치이고, 근거 없는 메모장은 기존 기능 어디와도 이어지지 않는다.
  - 스냅샷의 출처를 하나로 정해야 "당시 무엇을 봤나"가 분명하다.
- **틀렸을 때 비용:** 공시를 보기 전에 떠오른 생각을 적어 둘 곳이 없다. 사용자는 근거 모드로 질문 하나를 던진 뒤 기록하면 된다(질문 1회 비용). 근거 없는 메모 기능이 필요해지면 그때 마이그레이션으로 출처 구분 열을 더한다(지금 미리 두지 않는다 — 쓰지 않는 열은 검증되지 않은 약속이 된다).

### 결정 3-2. 진행 중 판정에서는 기록하지 않는다

- **추천:** `pending`·`running` 실행에서는 `판단 기록` 버튼을 비활성화한다("판정이 끝난 뒤 기록할 수 있습니다"). `done/partial/failed/limited/skipped`는 모두 허용한다. `failed/limited/skipped` 실행에서 만든 기록은 스냅샷에 판정 상태를 그대로 담고 화면에 "판정 없이 기록한 판단"이라고 표시한다.
- **근거:** 진행 중 스냅샷은 회색 점(⋯)만 담게 되어 나중에 다시 볼 가치가 없다. 반대로 판정이 실패했더라도 답변과 문단은 본 것이므로 기록을 막을 이유가 없다. ⊘(판정 불가)를 ❔로 바꿔 담지 않는다(A-2 spec 3.2 "판정 불가는 ❔와 다르다").
- **틀렸을 때 비용:** 판정을 기다리지 않고 바로 적고 싶은 사용자가 1~2초 기다린다(A-2 실행 p95 목표 1.5초).

### 결정 3-3. 같은 답변의 다른 판정 실행마다 기록이 따로 생길 수 있다(의도)

- **추천:** 유일 조건은 `(user_id, run_id)` 하나다. 같은 답변에 `retry`·`rejudge`로 새 실행이 생기면, 새 실행에서 또 기록을 만들 수 있다. 막지 않는다.
- **근거:**
  - 기록의 단위는 "답변"이 아니라 "사용자가 본 판정 화면"이다. `retry`는 ⊘였던 문장을 채우고, `rejudge`는 다른 정책으로 배지를 바꾼다. 다른 배지를 보고 내린 판단은 다른 기록이다.
  - 막으려면 메시지 id(`chat_id`)를 기록에 두고 원 실행 표와 맞춰 봐야 하는데, 원 실행은 스레드 삭제로 사라질 수 있다(2.1). 사라진 뒤에는 규칙을 지킬 근거가 없다.
  - 화면은 지금 보이는 실행(메시지의 최신 실행)에만 `판단 기록` 버튼을 그리므로, 두 번째 기록은 사용자가 다시 판정한 뒤 일부러 누를 때만 생긴다.
- **틀렸을 때 비용:** 같은 답변의 기록이 목록에 두 줄로 보일 수 있다. 각 줄에 당시 정책과 판정 시각이 보이므로 구별된다. 하나로 묶고 싶어지면 그때 메시지 id 열을 더한다.

### 3.1 사용자 시나리오

1. 사용자가 근거 모드에서 "삼성전자"를 고르고 "HBM 매출 비중과 주요 고객은?"을 묻는다. 답변 문장마다 ✅·⚠️·❔가 붙는다(A-2 흐름 그대로).
2. 요약줄 `AI 판정: ✅ 3 · ⚠️ 0 · ❔ 1 — 검색된 2025.12 사업보고서 문단 8개 기준` 옆의 `판단 기록` 버튼을 누른다.
3. 기록 양식이 답변 아래에 펼쳐진다.
   - **내 판단**(필수, 하나): `매수 검토` / `관망` / `제외`. 기본 선택 없음.
   - **기댄 문장**(선택, 여러 개): 답변 문장 목록에 체크박스. 각 문장 옆에 당시 배지가 함께 보인다.
   - **내 메모**(선택, 2,000자 이하).
   - **내 확신**(필수, 1~5).
   - **다시 볼 날짜**(선택): 날짜 입력과 빠른 선택 `1개월 뒤`·`3개월 뒤`.
   - 양식 머리 고지(결정 4-2)와 `저장` 버튼.
4. 저장하면 "판단을 기록했습니다 · 일지에서 보기" 토스트가 뜨고, 버튼이 `기록됨 · 일지에서 보기`로 바뀐다(같은 실행에 두 번째 기록을 만들지 않는다, 결정 5-2 유일 조건).
5. 석 달 뒤 사용자가 **판단 일지** 탭을 연다. 상단에 "다시 볼 날짜가 지난 기록 1건"이 보인다.
6. 기록을 열면 세 칸이 나란히(모바일은 위아래) 보인다.
   - **당시 판단:** 내 판단·확신·메모·기댄 문장.
   - **당시 근거(스냅샷):** 질문, `AI 생성 답변`, 문장별 당시 배지, 근거 문단 펼치기. 머리에 `당시 판정 정책 a2-v1 · 2026-10-04 판정` 표시.
   - **그 뒤 바뀐 것:** 적재된 보고서·근거 문단의 변화(결정 6-1)와 판정 정책 변화.
7. 사용자는 `다시 보기 기록 추가`로 새 판단(예: 관망 → 제외)과 메모를 덧붙인다. 이전 판단은 고쳐지지도 따로 지워지지도 않고 아래에 시간순으로 쌓인다(지울 때는 기록 전체, 결정 7-3).
8. 사용자는 `같은 질문 다시 묻기`로 근거 모드 채팅에 같은 회사·질문을 채워 넣을 수 있다. 보내기는 사용자가 누른다(새 판정 실행·한도는 A-2 경로 그대로). 새 답변에서 새 기록을 만든다.

## 4. 고지·AI 표시·투자 권유 아님

### 결정 4-1. 일지는 배지를 "당시 AI 판정"으로만 보여 주고 판단을 끌어내지 않는다

- **추천:**
  - 스냅샷의 배지 툴팁은 A-2 문구 그대로 "AI 판정(JEV 모델) · 검색된 공시 문단 기준이며 사실 여부를 보증하지 않습니다"를 쓰고, 머리에 "당시"를 붙인다(`당시 AI 판정`).
  - 기록 양식의 `내 판단`에는 **기본 선택이 없다.** 배지 개수에서 판단을 제안하지 않는다("✅가 많으니 매수 검토" 같은 문구·정렬·색 없음).
  - 일지 목록·상세 어디에도 "근거 점수", "판정 신뢰도 합계", ✅ 비율 같은 요약 숫자를 만들지 않는다.
  - 확신도 라벨 이름을 갈라 둔다: 서버가 내는 "AI 판정 확신도 높음/보통"(`records.py:212`)과 사용자가 고르는 "**내 확신** 1~5". 두 값을 같은 줄에 나란히 두지 않는다.
- **근거:** A-2 결과는 ✅ 정밀도 목표를 확인하지 못했고(관문 실패), 회사·부문 이름만 바꾼 문장이 자주 ✅로 넘어간다(`evidence-a2-interpretation.md:13,23`). 일지가 배지를 판단의 입력 점수처럼 다루면, 확인되지 않은 정밀도를 사실 보증처럼 쓰게 된다.
- **틀렸을 때 비용:** 사용자가 배지 요약을 직접 세야 한다(요약줄은 답변에 이미 있다). 판정 정밀도가 새 사전등록으로 확인되면 그때 요약 표시를 다시 검토한다.

### 결정 4-2. 고정 고지 문구

- **추천:** 일지 탭 머리와 기록 양식 머리에 같은 문구를 접지 않고 둔다.
  > 판단 일지는 내가 쓴 기록입니다. 답변과 배지는 AI가 만든 것으로, 배지는 검색된 공시 문단 기준 AI 판정(TypeSafe의 JEV 모델)이며 사실 여부를 보증하지 않습니다. 이 서비스는 투자 권유나 수익 예측을 하지 않으며, 투자 판단과 그 결과는 본인에게 있습니다. 이 프로젝트는 TypeSafe와 제휴 관계가 아닙니다.
- **근거:**
  - A-1 spec 11절 "정보 정리 도구다. 매수·매도 권유나 수익 예측을 하지 않는다"를 화면으로 옮긴다. 기존 화면의 고지 선례(`public/app.html:660`)와 같은 형식이다.
  - TypeSafe AUP 1.4는 AI 생성 여부를 오인하게 하는 것을 금지한다. 일지는 AI가 만든 것(답변·배지)과 사용자가 쓴 것(판단·메모)이 한 화면에 섞이므로 출처를 칸 머리마다 표시한다: `AI 생성 답변`, `당시 AI 판정`, `내 판단`, `내 메모`.
  - 이름은 사용한 기술을 설명하는 문장에만 쓰고 로고·"고객" 표현은 쓰지 않는다(A-1 spec 9절 16.4).
- **틀렸을 때 비용:** 화면 공간을 두 줄 쓴다. 접지 않는 이유는 일지가 "매수 검토" 같은 단어를 담는 유일한 화면이라서다.

### 결정 4-3. 가격·수익률을 일지에 붙이지 않는다

- **추천:** 기록 시점 주가, 이후 수익률, "판단 적중률"을 저장하거나 보여 주지 않는다. 모의투자 주문 버튼도 일지에 두지 않는다.
- **근거:** 가격을 붙이면 일지가 판단의 성과표가 되고, 성과표는 "어떤 판정을 따르면 수익이 났나"라는 투자 권유형 해석을 부른다. 판정 엔진은 공시 문단과 문장의 일치만 쟀고 투자 성과와의 관계는 잰 적이 없다. 또 시세 조회는 외부 요청이다.
- **틀렸을 때 비용:** 사용자가 판단 뒤 가격 흐름을 일지에서 바로 볼 수 없다. 기존 종목 화면(기업 지표)에서 따로 본다.

## 5. 데이터 모델

### 결정 5-1. 기존 포트폴리오·모의투자 모델은 재사용하지 않는다

- **추천:** 새 테이블 두 개(5-2)를 만든다. `Portfolio`·`Order`·`PaperAccount`·`RebalancePlan`에 열을 더하거나 FK를 걸지 않는다.
- **근거:**
  - 이 모델들은 체결된 주문·포지션·목표 비중이다(2.4). "매수 검토"는 주문이 아니라 판단이고, 판단을 주문 장부와 묶으면 일지가 매매 화면처럼 읽힌다(결정 4-3).
  - `RebalancePlan.targets`는 사용자당 1행 JSONB라 판단 이력을 쌓을 수 없다.
  - 모의투자 기능은 `compose.portfolio.yml` 실행 스택에서 동작 범위를 검증하지 않았다(`PORTFOLIO_LOCAL.md` 5절: "전체 원본 기능 … 검증하지 않았다"). 검증 안 된 기능에 새 기능을 매달지 않는다.
- **재사용하는 것:** `Base`·`UUIDPkMixin`·`CreatedAtMixin`(`app/models/base.py`), 인증 `get_current_user_any`, 소유자 확인 패턴(`_owned_run`, `_assert_owner`), 판정 직렬화 `records.serialize_claim`·`confidence_label`(스냅샷을 만들 때 한 번 부른다), 문단 저장소 `PassageStore.exists`·`existing`, P2 테스트 하네스 `tests/evidence/p2_support.py`.
- **틀렸을 때 비용:** 나중에 "판단 → 모의 주문" 연결을 원하면 `judgment_entries.id`를 주문 쪽에서 참조하는 열 하나로 붙인다. 반대 방향(일지가 주문을 참조)은 만들지 않는다.

### 결정 5-2. 테이블 두 개: 기록(스냅샷 고정) + 다시 보기 원장(덧붙이기만)

Alembic **`0010_judgment_journal`**(`down_revision = "0009"`)로 만든다.

`judgment_entries` — 판정 실행 하나에 대한 판단 기록 1건

| 열 | 형 | 설명 |
|---|---|---|
| `id` | UUID PK | |
| `user_id` | UUID FK → `users.id` | 소유자 |
| `run_id` | UUID, **FK 없음** | 원 판정 실행. 대화가 지워져도 기록은 남는다(결정 5-4) |
| `company`, `corp_code` | 문자열 | 목록 표시·회사 거르기용(스냅샷에도 있다) |
| `snapshot` | JSONB | 결정 5-3. 접수번호·정책 등 나머지는 모두 여기서 읽는다 |
| `snapshot_version` | 문자열(16) | 스냅샷 형식 이름 `c1` |
| `created_at` | 시각 | 기록 시각 |

- 색인: `(user_id, created_at)`, `(user_id, corp_code, created_at)`.
- 유일: `(user_id, run_id)` — 같은 실행에 기록 1건. 생각이 바뀌면 다시 보기 기록을 덧붙인다.

`judgment_updates` — 판단과 그 뒤 다시 보기(덧붙이기만 한다)

| 열 | 형 | 설명 |
|---|---|---|
| `id` | UUID PK | |
| `entry_id` | UUID FK → `judgment_entries.id` **ON DELETE CASCADE** | |
| `kind` | 문자열(16) | `initial`(기록 만들 때 1건) / `revisit`. CHECK 제약 |
| `decision` | 문자열(16) | `consider_buy`(매수 검토) / `watch`(관망) / `exclude`(제외). CHECK 제약 |
| `conviction` | 정수 1~5 | 내 확신(CHECK 제약) |
| `memo` | Text | 2,000자 이하(API 검증), 빈 문자열 허용 |
| `relied_claims` | JSONB | 기댄 문장 `idx` 목록(스냅샷 문장 범위 안인지 API가 확인) |
| `review_on` | Date, null | 다시 볼 날짜(KST 날짜) |
| `created_at` | 시각 | |

- 색인: `(entry_id, created_at)`. 소유자는 `judgment_entries.user_id`로 묶어 조회한다(update 쪽에 사용자 열을 두지 않는다).
- **현재 판단** = 그 기록의 가장 최근 update. **다시 볼 때 됨** = 최근 update의 `review_on`이 오늘(KST) 이하. 사용자당 기록이 수백 건 규모라 기록 색인 `(user_id, created_at)`으로 거른 뒤 계산한다. 느려지면 그때 색인을 더한다.
- **근거:**
  - 판단 일지의 가치는 "그때 무엇을 생각했나"를 사후에 고칠 수 없다는 데 있다. 판단을 덮어쓰는 수정 대신 덧붙이기만 하면, 나중에 본 정보로 당시 판단을 다듬는 사후 합리화가 구조적으로 막힌다. 이 저장소의 사전등록·원장 원칙(CLAUDE.md "실험 신뢰 장치")과 같은 생각이다.
  - 처음 판단도 같은 표의 `initial` 행으로 두면 판단 형태가 한 가지라 조회·내보내기가 단순하다.
- **틀렸을 때 비용:** 오타를 고칠 수 없어 사용자가 다시 보기 기록을 하나 더 쓴다. 기록 전체는 지울 수 있다(결정 7-3) — 개인 기록의 삭제권이 무결성보다 앞선다.
- **되돌리기:** `downgrade`는 두 표만 지운다. 기존 표는 바뀌지 않는다.

### 결정 5-3. 스냅샷은 참조가 아니라 복사다

- **추천:** 기록을 만들 때 서버가 DB의 원 실행·문장·메시지에서 스냅샷을 만들어 `snapshot`에 복사한다. 클라이언트가 보낸 스냅샷은 받지 않는다(요청 본문은 `run_id`와 판단 입력뿐).

`snapshot` 형식 `c1`:

```json
{
  "run": {"id": "...", "status": "done", "error_code": null, "trigger": "auto",
          "policy_version": "a2-v1", "jev_model": "jev-1.13.0", "generator_model": "llama3.1:8b",
          "created_at": "...", "finished_at": "..."},
  "company": "삼성전자", "corp_code": "00126380", "rcept_no": "20260312000123",
  "question": "HBM 매출 비중과 주요 고객은?",
  "answer": "…",
  "claims": [{"idx": 0, "text": "…", "start": 0, "end": 21, "status": "supported", "route": "jev",
              "reason": null, "source_idx": 1, "number_ok": [true, false, ...], "confidence": "높음"}],
  "passages": [{"passage_id": "...", "section": "II. 사업의 내용", "idx": 14, "sha256": "...", "text": "…"}]
}
```

- **담지 않는 것:** 문단별 확률 `s`·`c`, 어휘 점수 `lex`, `jev_request_key`, 지연·토큰. 화면이 쓰는 것은 상태·근거 문단·확신도 라벨뿐이고(A-2 spec 3.3: 확률 숫자는 노출하지 않는다), 일지는 내보내기를 하므로(결정 7-2) JEV 출력 원값을 사용자 파일로 흘리지 않는다(A-2 spec 7.4 "캐시를 학습·분석용 데이터로 내보내지 않는다", MCA 2.3(b)). `number_ok`는 로컬 숫자 확인 결과라 담는다(근거 문단의 숫자 굵게 표시에 쓴다).
- **근거:**
  - 원 실행은 스레드 삭제로 사라질 수 있고(2.1 cascade), 같은 메시지에 `retry`·`rejudge`로 새 실행이 생긴다. 실행을 가리키기만 하면 "당시 근거"가 지워지거나 다른 실행으로 바뀐다.
  - 확신도 라벨은 정책 표(`records.POLICIES`)에 의존한다. 나중에 정책 표에서 옛 정책이 빠지면 다시 계산할 수 없으므로 기록 시점 값으로 고정한다.
  - 문단 8개 × 600자 이하 + 답변이라 기록당 수 KB다.
  - 스냅샷 해시·손상 검사는 두지 않는다. 스냅샷은 서버만 쓰고 API로 고칠 길이 없으므로, 해시는 지켜 줄 위협이 없는 장치다.
- **틀렸을 때 비용:** 같은 문단 텍스트가 판정 기록과 일지에 두 번 저장된다(기록당 수 KB). 포트폴리오 규모에서 무시할 크기다.

### 결정 5-4. 원 대화가 지워져도 기록은 남는다

- **추천:** `run_id`에 FK를 걸지 않고, 메시지·스레드 id는 기록에 두지 않는다. 스레드 삭제는 기록을 지우지 않고, 기록 상세는 `run_id`로 원 실행 조회가 비면 "원래 대화는 삭제되었습니다"를 띄운다. 기록 삭제는 일지에서 따로 한다(결정 7-3).
- **근거:** 일지는 사용자가 명시적으로 남긴 기록이다. 대화 정리(스레드 삭제)가 판단 이력까지 지우면 일지의 목적이 무너진다. `evidence_runs.conversation_id`도 FK 없이 둔 선례가 있다(`app/models/evidence.py:26`).
- **틀렸을 때 비용:** 스레드를 지우면 질문·답변이 모두 사라진다고 기대한 사용자에게는 일지 사본이 남는다. 지금은 스레드 삭제 화면이 없고(2.1) API만 있으므로, 일지 도움말에 "대화를 지워도 일지 기록은 남습니다. 지우려면 일지에서 지우세요"를 적는다. 대화 삭제 화면을 만들게 되면 그 화면에 같은 문구를 둔다(그때 필요하면 스레드 id 열을 더한다).

### 결정 5-5. 기록 생성 규칙

1. `run_id`로 실행을 소유자 조건(`id`·`user_id`)으로 찾는다. 없으면 404.
2. 실행 `stale` 정리(`records.expire_stale`)를 먼저 적용한 뒤 상태를 본다. `pending`·`running`이면 409 "판정이 끝난 뒤 기록할 수 있습니다".
3. 같은 사용자·실행의 기록이 있으면 409와 기존 기록 id를 돌려준다.
4. 메시지(`chats`) 행에서 질문·답변을 읽는다. 없으면 409.
5. 스냅샷을 만들고(문장마다 `records.serialize_claim`에서 5-3 필드만 고른다), 기록 행과 `initial` update 행을 한 트랜잭션으로 저장한다.
6. `relied_claims`는 스냅샷 문장 `idx` 범위 안이고 `not_claim`이 아닌 것만 받는다. 아니면 422.
7. **검증 오류 응답에 메모를 되돌려 주지 않는다.** 일지 라우터는 본문을 직접 읽어 pydantic `model_validate`로 검사하고, 실패하면 칸 이름과 사유(`loc`, `msg`)만 담은 422를 돌려준다(`input` 없음). 메모 길이(2,000자)도 이 단계에서 같은 형식으로 거른다. 앱 전역 오류 처리기는 바꾸지 않는다(다른 라우터 응답이 바뀌지 않게).

### 결정 5-6. 기능 플래그

- **추천:** 새 설정 `JOURNAL_ENABLED`(기본 꺼짐). 일지 라우터 전체(조회·내보내기·삭제·생성)는 **`JOURNAL_ENABLED` 하나로만** 막는다(꺼지면 모든 경로 404, 근거 모드 라우터 `require_enabled`와 같은 방식). `EVIDENCE_CHAT_ENABLED`에 묶지 않는다.
  - 근거 모드가 꺼져 있으면: 생성은 원 실행이 있으면 그대로 된다(판정 표는 0009가 적용된 DB에 남아 있다). 변화 비교는 저장소가 연결되지 않으므로 `unavailable`, 화면은 `같은 질문 다시 묻기`를 숨긴다(3.2).
  - **"이 실행의 기록 있음" 표시는 한 곳에만** 붙인다: 판정 실행 직렬화 `records.serialize_run`의 `journal_entry_id`. 이 함수가 `GET /api/evidence/runs/{id}`(폴링)와 `GET /api/conversations/{cid}/evidence`(스레드 다시 열기)에 함께 쓰이므로 두 화면 경로가 같은 값을 본다(`app/routes/evidence.py:281,362`). 메시지 직렬화(`_serialize_message`)에는 붙이지 않는다. 조회는 `JOURNAL_ENABLED`일 때만 한다.
- **근거:**
  - 0010이 적용되지 않은 환경에서 판정 API가 깨지지 않게 하려면, A-2가 `EVIDENCE_CHAT_ENABLED`로 0009 표 조회를 막은 것(`conversations.py:93-96`)과 같은 보호가 필요하다.
  - 일지를 근거 모드 플래그에 묶으면, 근거 모드를 끄는 순간 사용자가 자기 메모를 보거나 내보내거나 지울 수 없게 된다. 삭제권(결정 7-3)은 다른 기능 상태에 기대면 안 된다.
- **틀렸을 때 비용:** 설정 하나가 늘어난다. 근거 모드 없이 일지만 켠 환경에서는 새 기록을 만들 화면이 없다(버튼이 근거 모드 답변에 있으므로) — 의도한 동작이다.

### 결정 5-7. 관리자 DB 초기화에 일지 표를 넣는다

- **추천:** `app/routes/admin.py`의 `USER_MODELS`에 `JudgmentUpdate`, `JudgmentEntry`를 이 순서로 더한다(자식 먼저). `/api/admin/reset`은 일지도 비우고, `/api/admin/stats`에는 두 표의 **행 수만** 나온다. 일지 내용을 보여 주는 관리자 경로는 만들지 않는다(결정 7-4).
- **근거:** 초기화는 이미 `chats`를 비운다(2.3). 관리자가 "사용자 자료를 비웠다"고 생각한 뒤에도 메모·질문 사본이 일지에 남으면 초기화의 의미가 어긋난다. 결정 5-4(대화를 지워도 기록은 남는다)는 사용자 자신의 정리 동작에 대한 규칙이고, 관리자 전체 초기화와는 다르다. 행 수는 내용이 아니라 이미 다른 사용자 표에도 쓰는 집계라 개인정보를 드러내지 않는다.
- **틀렸을 때 비용:** 시연 DB를 초기화하면 노아 자신의 일지도 지워진다. 초기화 전에 내보내기(결정 7-2)로 보관한다. 기존 코드가 비운 표 이름을 감사 로그(`admin.db_reset`)에 남기므로 일지 표도 그 목록에 나타나 흔적이 남는다.

### 5.1 API

| 메서드·경로 | 동작 |

## 6. 이후 공시 변화

### 결정 6-1. 변화는 "현재 적재된 문단과의 비교"로만 보여 준다

- **추천:** `GET /api/journal/{id}/changes`가 스냅샷과 문단 저장소의 현재 상태를 비교한다. 외부 호출(OpenDART·JEV·LLM) 없이 그 회사 문단의 Qdrant scroll 한 번(`existing(corp_code)`)만 쓴다. `companies()`(전체 scroll)는 쓰지 않는다.
  - **저장소 접근:** `app/routes/evidence.py`에 `get_passage_store()`(모듈 변수 `_passage_store`를 그대로 돌려줌)를 더해 일지 라우터가 의존성으로 받는다. 저장소를 두 곳에서 연결하지 않는다.
  - **확인 불가 판정을 먼저 한다:** 저장소가 None이거나, `exists()`가 거짓이거나, `exists()`·`existing()`이 예외를 내면 `{"status": "unavailable"}` 하나만 돌려준다. `existing()`은 컬렉션이 없을 때 빈 dict를 주므로(2.2), 이 확인 없이 비교하면 모든 문단이 "사라짐"으로 잘못 보인다.
  - **근거 문단 단위**(스냅샷 문단 8개 각각): "이 문단의 `sha256`이 현재 그 회사 문단들의 `sha256` 값 집합 안에 있는가"만 본다 → `same`("당시 문단이 지금도 적재되어 있습니다") / `gone`("당시 문단과 같은 본문이 지금 적재된 문단에 없습니다"). `passage_id`로 짝을 짓지 않는다. ✅·⚠️ 근거 문단은 맨 위에 둔다.
  - **보고서 단위:** 현재 문단들의 `rcept_no` 집합과 스냅샷 `rcept_no`를 비교 → `same`(집합이 스냅샷 값 하나뿐) / `replaced`("적재된 보고서가 바뀌었습니다: 당시 20260312000123 → 현재 …", 집합을 그대로 보인다) / `company_gone`(컬렉션은 있으나 그 회사 문단이 0개, 이때 문단은 모두 `gone`). 접수번호 변화는 **보고서 단위로만** 표시하고 문단 상태에 섞지 않는다(정정 보고서에서 본문이 같은 문단은 `same`이다).
  - **판정 정책:** 스냅샷 `run.policy_version`과 현재 `DEFAULT_POLICY.version` 비교 → 다르면 "당시 판정 기준 a2-provisional-2, 현재 a2-v1. 당시 배지는 당시 기준으로 보존됩니다." 일지는 다시 판정하지 않는다.
  - `gone` 문단의 대체 본문은 보여 주지 않고 표시와 `같은 질문 다시 묻기` 버튼만 둔다.
- **근거:**
  - `passage_id`는 위치 이름이고 `sha256`은 본문만의 해시다(2.2). 위치로 짝을 지으면 문단 하나가 끼어들거나 보고서가 바뀔 때 뒤쪽 문단이 모두 "바뀜"으로 보이는 거짓 변화가 난다. 본문이 지금도 어딘가 적재되어 있는지만 보면 위치 이동에 흔들리지 않는다. 대가로 "어느 문단으로 바뀌었나"는 말하지 못하는데, 결정상 새 본문을 보여 주지 않으므로 필요 없다.
  - 저장소는 회사당 한 보고서 상태만 둔다(2.2). 그래서 감지할 수 있는 것은 "재적재로 문단이 바뀌었다"(정정 공시, 새 사업보고서 적재)이고, 적재되지 않은 새 공시(분기·반기보고서, 주요사항보고서)는 알 수 없다. 이 한계를 화면 도움말에 그대로 쓴다: "이 비교는 이 앱에 적재된 사업보고서 문단만 봅니다. 그 밖의 새 공시는 확인하지 않습니다." 지금 적재기에는 기간 인자가 없어 새 사업보고서를 적재할 수도 없다(2.2) — 그 전까지 실데이터에서는 `same`만 나온다.
  - 바뀐 근거의 새 본문을 옛 배지 옆에 두면, 옛 판정이 새 문단에도 해당하는 것처럼 읽힌다. 새 근거는 새 질문(새 판정 실행)으로만 본다.
  - 확인 불가를 "변화 없음"과 섞지 않는다(A-2 spec 3.2의 ⊘ ≠ ❔ 원칙).
- **틀렸을 때 비용:** 본문이 한 글자만 고쳐져도 `gone`이 된다(공백·표 형식 정리 포함). 정정 공시의 사소한 수정도 "같은 본문이 없음"으로 보이지만, 표시 문구가 "같은 본문"을 말하므로 사실과 어긋나지 않는다. 사용자가 "새 공시가 없다"로 오해할 위험은 도움말과 "적재된 보고서 기준" 표시로 막는다.

### 결정 6-2. 비교 결과는 저장하지 않는다

- **추천:** 변화 비교는 상세를 열 때마다 새로 계산하고 DB에 쓰지 않는다.
- **근거:** 기록당 Qdrant scroll 1회(그 회사 문단 수백 개, payload 3필드)라 가볍다. 저장하면 "언제 기준 비교인가"를 다시 관리해야 한다.
- **틀렸을 때 비용:** 목록 화면에서 "바뀐 기록만" 거르기를 할 수 없다. 필요해지면 목록에 나온 회사만큼 `existing()`을 읽어 보고서 단위 `replaced` 표시를 붙인다.

## 7. JEV 활용, 개인정보, 삭제·내보내기

### 결정 7-1. 일지에서는 JEV를 새로 부르지 않는다

- **추천:** 이 spec의 P1~P4에서 일지의 어떤 기능도 JEV를 부르지 않는다. "내 메모가 근거 문단과 맞는가" 판정, 다시 보기 때 자동 재판정을 만들지 않는다. 근거가 `gone`이 된 ✅ 문장의 재판정은 시작 조건이 갖춰질 때만 여는 조건부 후속 단계 P5로 미룬다(결정 9-1). 일지는 기존 판정 결과를 **스냅샷으로 보존해 보여 주기만** 한다. 따라서 `Quota` 소모는 0이다.
- **근거:**
  1. **외부 전송:** JEV 호출은 state 문자열 전체를 TypeSafe로 보낸다(`jev_service.py:143-150`, `judge.py:37`). 메모를 판정하려면 메모를 state에 넣어야 한다. A-2는 사용자 질문 원문조차 보내지 않도록 설계했다(A-2 spec 8절: "사용자 질문 원문은 보내지 않는다"). 메모는 질문보다 더 사적인 글(보유 여부, 매수 금액 계획, 개인 사정)이 들어가기 쉬운 칸이다.
  2. **측정 없음:** 판정 엔진은 "생성기가 문단 8개를 보고 쓴 문장"에서만 쟀다(A-1·A-2). 사용자 메모는 의견·계획·추측 문장이 대부분이라 A-1 라벨 정의상 "비주장"이고, 메모 대 문단 판정력은 잰 적이 없다. 측정되지 않은 조건에 배지를 붙이면 결정 4-1과 정면으로 어긋난다.
  3. **약점과 겹침:** 메모는 답변 문장을 바꿔 쓰는 경우가 많고, 주체·부문을 바꾼 문장의 정확도가 0.57이었다. 메모에 붙은 ✅는 "내 생각이 공시로 확인됐다"로 읽히기 가장 쉬운 자리다.
- **부른다면 지켜야 할 조건(이번에는 만들지 않는다, 기록만):** 새 사전등록(메모형 문장 표본, AI 참조 라벨, 비주장 비율)으로 판정력을 먼저 잰다 → 메모 외부 전송에 별도 동의(A-2 고지와 다른 버전 번호) → 호출은 기존 `Quota`(`jev_service.py:54`)를 그대로 쓰되 실행당 1회, 사용자 일일 호출 상한 안에서 센다 → 결과는 `AI 판정(메모)` 라벨로 기존 배지와 다른 모양. 이 조건이 갖춰지기 전에는 만들지 않는다.
- **틀렸을 때 비용:** 사용자가 메모와 근거의 어긋남을 스스로 확인해야 한다. 일지 상세는 기댄 문장과 그 근거 문단을 나란히 보여 주므로 대조할 재료는 화면에 있다. 메모 판정은 판정력 측정이 끝나면 위 조건으로 붙일 수 있다.

### 결정 7-2. 내보내기: 내 기록 전부, JSON 하나, JEV 원값 제외

- **추천:** `GET /api/journal/export`는 기록마다 스냅샷 전체와 update 전부를 JSON 하나로 돌려준다(파일명 `lumina-journal-YYYYMMDD.json`). 최상위 `notice` 필드에 4-2 고지를 담고, AI가 만든 칸(답변·문장 상태·확신도 라벨)에 `"ai_generated": true` 표시를 단다. CSV는 만들지 않는다.
- **근거:** 사용자 자료는 사용자가 가져갈 수 있어야 한다. 스냅샷에 `s`·`c`가 없으므로(5-3) 내보내기에도 JEV 확률 원값이 없다. 상태 라벨(✅ 등)은 화면에 보이는 정보라 담는다. CSV는 스냅샷 구조(문장 목록·문단 목록)를 한 줄로 펴면서 AI 표시를 열 이름으로 흉내 내야 해 형식 결정이 하나 더 생긴다. 가져가기 목적에는 JSON으로 충분하다.
- **틀렸을 때 비용:** 스프레드시트로 보고 싶은 사용자가 JSON을 변환해야 한다. 필요해지면 JSON에서 만드는 CSV를 따로 더한다. 확률이 필요한 고급 사용자는 판정 기록 API(`GET /api/evidence/runs/{id}`, 원 대화가 있을 때)에서 본다.

### 결정 7-3. 삭제

- **추천:** 기록 단위 삭제와 전체 삭제(확인 필요) 두 가지를 둔다. 모두 즉시 물리 삭제(soft delete 없음)다. update 1건 삭제는 두지 않는다 — 판단 원장에서 한 줄만 빼면 남은 기록이 당시 생각을 왜곡하고(결정 5-2), 지우고 싶은 메모는 기록 전체를 지워 없앤다.
- **근거:** 이 앱에는 계정 삭제 API가 없다(2.3). 일지는 개인 메모를 담으므로 사용자가 스스로 지울 수단이 일지 안에 있어야 하고, 그 수단은 근거 모드 플래그와 무관하게 동작한다(결정 5-6).
- **틀렸을 때 비용:** 잘못 지우면 복구할 수 없다. 화면은 삭제 전에 확인 대화상자를 띄우고, 전체 삭제는 "전체 삭제"를 입력해야 API(`?confirm=delete-all`)를 부른다. 메모 한 줄만 지우고 싶은 사용자는 기록 전체를 잃는다 — 내보내기 뒤 지우는 길을 도움말에 적는다.

### 결정 7-4. 메모는 어디로도 나가지 않는다

- **추천:**
  - 메모·질문·답변은 JEV, Ollama(LLM·임베딩), 알림 `dispatch`, 감사 로그 `payload`, 구조화 로그 어디에도 넣지 않는다.
  - **다시 볼 날짜 알림은 앱 안에서만** 한다: 일지 탭 점 표시와 목록의 `due_count`. 스케줄러·텔레그램·이메일·SMS를 쓰지 않는다.
  - 감사 로그에는 사건 종류와 개수만 남긴다: `journal.create`(`{entry_id}`), `journal.delete`(`{count}`), `journal.export`(`{count}`).
  - 검증 오류 응답에도 메모를 되돌려 주지 않는다(결정 5-5의 7).
  - 관리자 화면에 일지 내용을 보는 경로를 만들지 않는다. 관리자에게 보이는 것은 기존 `/api/admin/stats`의 행 수뿐이다(결정 5-7).
- **근거:** 알림 채널은 모두 외부 서비스다(2.3). 다시 볼 날짜에 메모를 담아 보내면 사용자의 투자 생각이 제3자 서비스에 남는다. 감사 로그 `payload`는 JSONB를 그대로 저장하고 관리자 감사 로그 조회가 그대로 돌려주므로(`app/routes/admin.py:52-78`), 메모를 넣으면 관리자에게 보이고 일지 삭제 뒤에도 남는다. A-2 spec 7.5 "남기지 않는 것"(주장 원문·질문)과 같은 원칙이다.
- **틀렸을 때 비용:** 앱을 열지 않으면 다시 볼 날짜를 놓친다. 필요해지면 메모 없이 "다시 볼 기록 N건" 숫자만 보내는 알림을 따로 설계한다(범위 밖).

## 8. 평가

### 결정 8-1. 통계 평가를 하지 않는다. 기능 수용 기준으로 대신한다

- **추천:** 사전등록·홀드아웃 같은 통계 평가를 두지 않는다. 대신 아래 수용 기준을 단위·DB 테스트로 확인한다.
- **근거:** 평가는 모델이나 규칙이 어떤 성능을 낸다는 주장을 검증하려고 한다. 일지는 새 모델 출력을 만들지 않고(결정 7-1), 판단을 추천하지 않고(결정 4-1), 성과를 재지 않는다(결정 4-3). 검증할 성능 주장이 없다. "판단 적중률"이나 "✅가 많은 답변 뒤 판단의 수익" 같은 지표는 투자 권유형 해석을 부르므로 일부러 재지 않는다.
- **틀렸을 때 비용:** 일지가 실제로 쓸모 있는지(다시 열어 보는가)는 모른다. 포트폴리오 시연 규모에서는 사용 통계가 의미 있는 표본이 되지 않는다. 사용자가 늘면 "다시 볼 날짜가 지난 기록 중 열어 본 비율"을 개인정보 없이 집계하는 것을 별도로 검토한다.

### 8.1 수용 기준 (단계별 완료 기준에 쓴다)

1. 기록 생성 뒤 원 스레드를 SQL `DELETE` 경로로 지워도 기록 상세가 같은 스냅샷을 돌려주고 `source_available=false`다.
2. 같은 메시지에 `retry`·`rejudge` 실행이 새로 생겨도 기록은 처음 실행의 문장 상태를 그대로 보여 준다.
3. 스냅샷·내보내기 어디에도 `s`, `c`, `lex`, `jev_request_key` 키가 없다.
4. `pending`·`running` 실행으로 만들기 409, 같은 실행 두 번째 기록 409, 남의 실행·기록 404.
5. 변화 비교: 스냅샷 `sha256`이 현재 값 집합에 있으면 `same`, 없으면 `gone`. 문단이 하나 끼어들어 `passage_id`가 밀린 경우에도 본문이 같은 문단은 `same`. 접수번호만 바뀐 경우 문단은 `same`, 보고서는 `replaced`. 저장소 없음·컬렉션 없음(`exists()` 거짓)·예외 → `unavailable` 하나(문단 상태가 하나도 섞이지 않음). 회사 문단 0개 → `company_gone`.
6. 다시 보기 update는 기존 행을 바꾸지 않는다(행 수만 는다). update 1건 삭제 경로가 없다.
7. 메모를 담은 요청 뒤 감사 로그 `payload`, 로그 출력, **검증 오류(422) 응답 본문** 어디에도 메모 문자열이 없다(필수 칸 누락·메모 길이 초과·잘못된 `decision`으로 확인).
8. 일지 코드 경로에서 JEV 클라이언트·LLM 클라이언트·`notification.dispatch`가 한 번도 불리지 않는다(가짜 객체 호출 수 0).
9. `JOURNAL_ENABLED` 꺼짐 → 모든 일지 경로 404, 판정 API가 0010 표를 조회하지 않는다. `JOURNAL_ENABLED` 켜짐·`EVIDENCE_CHAT_ENABLED` 꺼짐 → 목록·상세·내보내기·삭제가 동작하고 변화 비교는 `unavailable`.
10. 기존 `tests/evidence`와 저장소 전체 테스트가 그대로 통과한다(**모든 단계**의 완료 기준).
11. 전체 삭제는 `confirm=delete-all` 없이는 400이고 아무것도 지우지 않는다. 관리자 초기화가 일지 두 표를 비운다.
12. `decision`·`kind` CHECK 제약이 잘못된 값을 DB 수준에서 거부한다.

- 메모 판정·자동 재판정 — 결정 7-1의 조건이 갖춰질 때 별도 spec. `gone` 근거 ✅ 문장의 사용자 요청 재판정은 결정 9-1의 조건부 P5.

- 모듈 B(뉴스 판단 피드).

### 결정 9-1. 조건부 후속 단계 P5: 근거가 사라진 ✅ 문장의 사용자 요청 재판정

- **시작 조건(모두 충족 전에는 착수하지 않는다):**
  1. 적재기에 보고서 기간 인자가 생기고(2.2: 지금은 2025.12 고정), 2026.12 사업보고서가 실제로 적재되었다. 그 전에는 `gone`이 실데이터에서 생기지 않아 기능을 확인할 수 없다.
  2. P1~P4가 머지되었다.
- **추천 범위:**
  - 대상은 스냅샷에서 ✅였고 그 근거 문단이 결정 6-1에서 `gone`인 문장뿐이다. 자동 실행은 없고, 사용자가 문장 옆 `현재 공시로 다시 확인`을 눌러야 부른다.
  - 보내는 것은 A-2와 같은 state(회사명, **스냅샷의 AI 답변 문장 하나**, 현재 적재 문단에서 검색한 문단 8개)뿐이다. **메모와 질문은 보내지 않는다**(문단 검색에는 문장 자체를 쓴다).
  - 호출은 기존 `Quota`(`jev_service.py:54`)를 그대로 거친다: 문장 1개 = 호출 1회, 사용자 일일 상한·전역 상한 안. 한도 초과면 호출하지 않고 "오늘 판정 한도에 도달했습니다".
  - 결과는 새 update 종류 `ai_recheck`로 덧붙인다(그 마이그레이션은 P5의 것이다: `kind` CHECK 확장, 결과 JSONB 열 추가). 담는 것은 문장 idx, 상태, 현재 근거 문단(`rcept_no`·`sha256`·본문), 정책, 시각이고 `s`·`c`는 담지 않는다. **스냅샷은 바꾸지 않는다.**
  - 화면 표시: "현재 적재 문단 기준 AI 재판정 · 이 조건(근거가 바뀐 문장 재판정)의 정확도는 측정되지 않았습니다". 당시 배지 옆이 아니라 다시 보기 원장 줄에 둔다.
- **측정:** P5를 켜기 전에 재판정 조건(옛 답변 문장 × 새 보고서 문단)의 판정력을 새 사전등록으로 잰다. 측정 전에는 위 "측정되지 않았습니다" 표시를 떼지 않는다.
- **근거:** 결정 7-1의 거부 이유 중 외부 전송(메모)과 측정 없음(메모형 문장)은 이 경우에 해당하지 않는다 — 보내는 문장은 A-2가 이미 보낸 AI 답변 문장이고, 판정 대상도 A-2가 잰 "생성기 문장 × 사업보고서 문단"에 가깝다. 다만 문단이 다른 연도 보고서라는 점은 잰 적이 없어 표시와 사전등록이 필요하다.
- **틀렸을 때 비용:** 시작 조건이 오래 안 갖춰지면 `gone` 문장은 "같은 질문 다시 묻기"로만 확인한다(새 답변·새 판정 전체를 쓰므로 호출이 더 든다).
