## 1. 목적과 범위

AI 채팅 답변의 **문장마다** 다음 셋 중 하나를 붙이고, 근거 문단을 펼쳐 볼 수 있게 한다.

| 배지 | 판정 | 화면 문구(사실 여부가 아니라 검색 문단 기준임을 드러낸다, A-1 spec 11절) |
|---|---|---|
| ✅ | 지지됨 | 검색된 공시 문단에서 확인됨 |
| ⚠️ | 반박 | 검색된 공시 문단과 어긋남 |
| ❔ | 근거 없음 | 검색된 공시 문단에서 확인되지 않음 |

판정 엔진(A-1: `app/services/evidence/`, `app/lib/jev.py`)은 그대로 재사용하고, 이 spec은 **채팅 연결**(화면, API, 저장, 장애·한도, 관측)과 **연결 전에 끝내야 할 평가 두 가지**(✅ 임계값 재설정, 계층형 판정 검증)를 정한다.

## 3. 사용자 시나리오와 화면 상태

### 결정 3-1. 판정은 "공시 근거 모드"에서만 한다

- **추천:** 채팅 입력창 위에 **공시 근거 모드** 토글과 **회사 선택**(자동완성)을 둔다. 모드를 켜고 회사를 고른 질문만 근거 판정 경로로 보낸다. 모드를 끈 질문은 지금처럼 ReAct 에이전트가 답하고 배지를 붙이지 않는다(상태 "판정 대상 아님", 배지 영역 자체를 그리지 않음).
- **근거:**
  - 에이전트 답변은 시세·CB 통계·상품 검색 같은 도구 결과에서 나온다(2.1). 사업보고서 문단으로 지지될 수 없는 문장이 대부분이라, 판정하면 ❔가 쏟아져 "근거 없는 답변"으로 오해를 산다.
  - A-1이 판정력을 잰 조건은 "사업보고서 문단 8개를 보고 쓴 답변"이다. 그 조건 밖의 답변에 같은 임계값을 쓰면 측정값이 보증하지 않는다.
  - 회사를 질문 문장에서 자동 추출하면 오인식이 곧 엉뚱한 공시로 이어진다. 명시적 선택은 오류 경로를 없앤다.
- **틀렸을 때 비용:** 사용자가 모드 전환을 번거롭게 느낄 수 있다(클릭 1~2회). 자동 감지는 나중에 선택 기본값을 채우는 보조 기능으로만 붙일 수 있고, 그때도 판정 경로는 바뀌지 않는다.

회사 선택 후보는 `evidence_passages`에 문단이 적재된 회사로 한정한다(6절 결정 6-4). 처음 적재 대상은 보일러플레이트 시드 15개사다(`app/services/graph_service.py` `_COMPANIES`). 자동완성은 기존 `search_companies`(`app/services/krx_companies.py:101`) 결과를 적재 목록과 교집합해 보여 준다.

### 3.1 사용자 시나리오

1. 사용자가 공시 근거 모드를 켜고 "삼성전자"를 고른 뒤 "주요 제품과 매출 비중은?"을 묻는다.
2. 화면에 질문이 올라가고 "공시 문단 검색·답변 생성 중…" 표시가 뜬다.
3. 답변이 문장 단위로 나뉘어 그려진다. 문장마다 회색 점 배지(판정 중)가 붙는다. 답변 머리에 `AI 생성 답변` 표시가 있다.
4. 1~2초 안에 배지가 ✅·⚠️·❔로 바뀐다. 답변 아래에 요약줄 `AI 판정: ✅ 3 · ⚠️ 0 · ❔ 1 — 검색된 2025.12 사업보고서 문단 8개 기준`이 뜬다.
5. ✅ 또는 ⚠️ 배지를 누르면 근거 문단이 펼쳐진다(보고서 접수번호, 절, 문단 본문). ❔를 누르면 "검색된 문단 8개에서 이 문장을 확인하지 못했습니다"와 검색 문단 목록(접힘)을 보여 준다.
6. 대화 목록에서 이 스레드를 다시 열면 같은 배지와 근거가 저장된 판정 기록에서 다시 그려진다(5.4절).

### 3.2 화면 상태

메시지 단위 상태(판정 실행 1건)와 문장 단위 상태를 나눈다.

| 단위 | 상태 | 화면 | 진입 조건 |
|---|---|---|---|
| 메시지 | `pending` / `running` | 문장 배지 모두 회색 점(⋯), 요약줄 "AI 판정 중…" | 답변 저장 직후 |
| 메시지 | `done` | 문장 배지 확정, 요약줄 개수 표시 | 모든 문장이 문장 단위 종결 상태 |
| 메시지 | `partial` | 확정된 문장은 배지, 나머지는 "판정 불가"(회색 ⊘). 요약줄 끝에 "일부 문장은 판정하지 못했습니다" | 마감 시간 초과·일부 호출 실패 |
| 메시지 | `failed` | 모든 문장 회색 ⊘, 요약줄 "근거 판정을 하지 못했습니다(일시적 오류). 답변은 판정 없이 표시됩니다." + `다시 판정` 버튼 | 첫 호출부터 연속 실패, 키·설정 오류 |
| 메시지 | `limited` | 모든 문장 회색 ⊘, 요약줄 "오늘 판정 한도에 도달해 판정을 생략했습니다." | 일일 한도 초과(7.2절) |
| 메시지 | `skipped` | 배지 없음, 요약줄 "개인정보로 보이는 내용이 있어 외부 판정을 생략했습니다." | 전송 전 개인정보 패턴 탐지(8절) |
| 문장 | `supported` | ✅ | SYS 지지됨 |
| 문장 | `contradicted` | ⚠️ | SYS 반박 |
| 문장 | `no_evidence` | ❔ | SYS 근거 없음, 또는 1차 필터 하단 구간(6절) |
| 문장 | `not_claim` | 배지 없음, 옅은 글씨 | 비주장 문장 규칙(5.2절) |
| 문장 | `unjudged` | ⊘ "판정 불가" | 해당 주장의 호출 2회 실패, 마감 초과, 주장 수 상한 초과 |

- **판정 불가는 ❔와 다르다.** ❔는 "봤는데 없었다", ⊘는 "보지 못했다"다. 둘을 합치면 장애가 "근거 없음"으로 둔갑한다.
- `다시 판정` 버튼은 `failed`·`partial`에서만 보이고, 새 판정 실행을 만든다(기존 실행은 타임라인에 남는다, 5.4절). 한도 상태에서는 숨긴다.

### 3.3 근거 문단 펼치기

- 펼친 칸 머리: `근거 문단 · 2025.12 사업보고서(접수번호 20260312000123) · II. 사업의 내용 · 문단 14` 형식.
- 본문: 판정 당시 저장한 문단 스냅샷(5.4절)을 그대로 보여 준다. 주장과 겹치는 숫자는 굵게 표시한다(숫자 존재 확인을 통과한 값만, `numbers.number_check` 기준).
- 지지 확률은 숫자로 보여 주지 않는다. 대신 배지 툴팁에 "AI 판정 확신도: 높음/보통" 두 단계만 쓴다(τ_s 이상 0.15 구간 안이면 보통). 확률 숫자를 노출하면 사용자가 "81% 사실"로 읽는다.
- **틀렸을 때 비용:** 확률을 감추면 고급 사용자가 경계 사례를 구분하기 어렵다. 판정 기록 API에는 확률을 남기므로(5.4절) 나중에 개발자 보기에서 꺼낼 수 있다.

### 3.4 AI 판정임을 표시 (TypeSafe AUP 1.4)

AUP 1.4는 AI 생성 여부를 오인하게 하는 것을 금지한다. A-1 spec 9절은 "답변 자체와 판정 배지 모두에 AI 생성임을 표시"로 정했다.

- 답변 말풍선 머리: `AI 생성 답변` 라벨(모드와 무관하게 모든 답변에 붙인다 — 기존 화면에도 없으므로 같이 고친다).
- 요약줄은 항상 `AI 판정:`으로 시작한다.
- 배지 툴팁: "AI 판정(JEV 모델) · 검색된 공시 문단 기준이며 사실 여부를 보증하지 않습니다".
- 모드 토글 옆 도움말: "판정에는 TypeSafe의 JEV 모델을 사용합니다. 이 프로젝트는 TypeSafe와 제휴 관계가 아닙니다." 이름은 기술을 설명하는 문장에만 쓰고 로고·"고객" 표현은 쓰지 않는다(A-1 spec 9절 16.4).

## 4. 아키텍처

### 결정 4-1. 결합 방식: 답변 먼저 반환, 판정은 앱 프로세스 안 비동기 작업 + 폴링

- **추천:** 근거 모드 요청은 **검색 → 생성 → 저장**까지 동기로 끝내고 답변·문장 목록·판정 실행 id를 바로 돌려준다. 판정은 답변 저장 직후 **FastAPI 프로세스 안 `asyncio` 백그라운드 작업**으로 시작하고, 프런트가 판정 실행을 짧게 폴링해 배지를 채운다.
- **근거:**
  - 판정 지연은 생성 지연보다 훨씬 작다. 주장 p95 5개를 동시성 3으로 보내면 두 묶음 × 호출 p95 401ms ≈ 0.8초다(7.1절). 반면 로컬 생성은 수 초 이상이다. 동기 결합(판정 끝까지 기다렸다 반환)은 답변 표시를 판정 지연·장애에 묶는다. JEV가 느리거나 죽어도 답변은 떠야 한다.
  - **스트리밍 후 후속 판정은 이 저장소에 붙일 곳이 없다.** 스트리밍 경로가 하나도 없고(2.1), `generate_answer`도 한 번에 돌려준다. 스트리밍 도입은 생성기 클라이언트(`app/lib/llm_client.py`의 provider 4종)를 모두 바꾸는 일이라 A-2의 목적(판정 연결)과 무관한 위험을 키운다. 또 문장이 완결되기 전에는 판정할 수 없으므로 스트리밍이 판정 체감을 앞당기는 폭은 작다.
  - 실제 실행 스택(`compose.portfolio.yml`)에는 Celery worker가 없다(2.1, `PORTFOLIO_LOCAL.md:21,113`). Celery를 전제하면 판정을 위해 worker·브로커 구성을 새로 들여야 하고, 기존 `/api/chat/async`도 이 스택에서 쓰이지 않는다. 판정 작업은 짧고(p95 약 1초) 대부분 네트워크 대기라 앱 이벤트 루프 안에서 돌려도 요청 처리를 막지 않는다.
- **세부:**
  - 답변 행·실행 행(`pending`)을 커밋한 **뒤** `asyncio.create_task`로 판정 실행을 시작한다. 작업 참조는 모듈 수준 집합에 보관해 가비지 컬렉션으로 사라지지 않게 하고, 끝나면 뺀다. 작업은 요청 세션이 아니라 자기 DB 세션을 연다.
  - JEV 호출은 비동기 `httpx.AsyncClient`로 하고, `asyncio.Semaphore(3)`으로 실행 안 동시성을 3으로 묶는다. 프로세스 전체 동시 JEV 호출은 `Semaphore(6)`으로 한 번 더 묶는다.
  - **재시작 복구:** 앱 시작(lifespan) 시 `pending`·`running`으로 남은 실행을 모두 `failed`(`stale`)로 바꾼다. 실행 중 프로세스가 죽은 경우는 7.3절의 "60초 지난 `pending`·`running`은 조회 시 `stale`" 규칙이 함께 덮는다. 사용자는 `다시 판정` 버튼으로 복구한다. **자동 재큐잉은 하지 않는다**(재시작 직후 몰리는 호출이 한도를 갉아먹고, 사용자가 이미 떠난 대화에 호출을 쓰게 된다).
  - 폴링은 범용 `GET /api/tasks/{id}`가 아니라 **판정 실행 조회** `GET /api/evidence/runs/{run_id}`로 한다. 결과의 진실 원천이 DB 판정 기록이어야 대화를 다시 열 때와 같은 데이터를 본다.
  - 폴링 간격 500ms, 최대 15초. 15초가 지나도 `pending`·`running`이면 프런트는 폴링을 멈추고 "판정이 지연되고 있습니다" + `새로고침` 링크를 보여 준다(서버 쪽 마감은 7.1절 8초이므로 정상이라면 일어나지 않는다).
- **틀렸을 때 비용:** 재시작·배포 중이던 판정은 사라지고 사용자가 `다시 판정`을 눌러야 한다(포트폴리오 규모에서 드물다). 다음 중 하나가 생기면 작업 큐(Celery 등, 기존 `app/celery_app.py` 재사용)로 옮긴다: ① 앱을 여러 프로세스(uvicorn worker 2개 이상)나 여러 인스턴스로 띄울 때 — 시작 시 `stale` 처리가 다른 프로세스의 진행 중 실행을 죽이므로, 그 전에 반드시 옮긴다. ② 지표 `evidence_start_delay_ms`(7.5절) p95가 500ms를 넘을 때 — 이벤트 루프가 판정 작업에 밀리고 있다는 뜻이다. 옮길 때 바뀌는 것은 실행기 호출부 한 곳이고, 실행 상태·저장·API는 그대로다.

### 결정 4-2. 근거 모드 답변은 `generate_answer`로 만든다 (에이전트 아님)

- **추천:** 새 라우터 `app/routes/evidence.py`에 `POST /api/evidence/chat`을 둔다. 회사 문단 검색 → `generate_answer`(A-1 공용 함수) → 문장 분해 → 저장 → 판정 작업 등록 순서다. 생성 모델은 `settings.EVIDENCE_LLM_MODEL`(새 설정, 기본값은 6절 평가에 쓴 서비스 생성기 태그)로 따로 둔다.
- **근거:**
  - 판정 대상 답변이 "문단 8개를 보고 쓴 답변"이어야 A-1·A-2 평가가 제품을 보증한다(결정 3-1).
  - 기존 `/api/chat`과 에이전트를 건드리지 않으므로 CB·상품 탭(2.1) 회귀 위험이 없다.
  - 생성 모델을 앱 기본 `LLM_MODEL`과 분리해야 임계값이 묶인 생성기(6.3절)가 다른 기능 설정 변경에 끌려가지 않는다.
- **같은 스레드에 저장한다.** 근거 모드 메시지도 `chats` 행으로 같은 `conversation_id`에 저장하고(`steps=[]`, `citations`에 문단 8개 참조), 응답에 `chat_id`를 포함한다. 그래야 대화 목록·이력·후속 질문 문맥이 하나로 이어진다. `conversation_id` 결정 로직은 `chat.py`의 `_get_or_create_conversation`을 공용 모듈로 옮겨 함께 쓴다.
- **이력 문맥:** `generate_answer`는 이력을 받지 않는다. 근거 모드는 질문 하나에 문단 8개로 답하는 단발형으로 둔다. 이전 답변을 문맥에 섞으면 답변 문장이 검색 문단 밖에서 올 수 있어 ❔가 늘고, A-1 조건과도 달라진다.
- **틀렸을 때 비용:** 근거 모드에서 "그럼 작년은?" 같은 후속 질문이 문맥 없이 처리된다. 화면 안내 문구("근거 모드는 질문마다 새로 검색합니다")로 기대를 맞춘다.

- **`JevClient`를 고치지 않고 감싸지도 않는 이유:** `JevClient`는 호출 기록 파일이 캐시·토큰 원장을 겸하는 평가용 설계다(2.2). 제품 판정은 비동기 호출이어야 하고, 여러 프로세스로 늘리면 같은 파일에 쓰는 원장이 섞이고 상한을 프로세스마다 따로 센다. 평가 재현성을 지키려면 그대로 두고, 제품 쪽은 같은 요청 키·응답 검증 함수를 import해 판정 결과가 비트 단위로 같도록 한다.
- **틀렸을 때 비용:** 재시도·검증 로직이 두 곳에 생긴다. 응답 검증(`parse_answers`)과 요청 키(`request_key`)는 공유하므로 판정 의미가 갈라지지 않는다. 재시도 루프 10여 줄만 중복이다.

- **틀렸을 때 비용:** 테이블 두 개와 마이그레이션 하나가 늘어난다. 되돌리기는 `downgrade`로 두 테이블을 지우면 끝이고 `chats`는 바뀌지 않는다.

## 5. 판정 실행 규칙

### 5.1 순서

1. 답변을 `claim_spans`로 나눈다.
2. 비주장 규칙(5.2절)에 걸린 문장은 `not_claim`.
3. 개인정보 패턴(8절)이 답변에 있으면 실행 전체를 `skipped`로 끝낸다.
4. 주장마다 숫자 확인과 1차 필터 점수를 계산한다(로컬, 수 ms).
5. 정책 `policy_version`이 1차 필터를 켠 경우(6절 결과에 따름) 하단 구간은 `no_evidence`(route `lex_low`), 상단 구간은 `supported`(route `lex_high`)로 확정한다.
6. 나머지 주장은 `ServiceJevClient`로 판정한다. 동시성 3, 실행 마감 8초.
7. `sys_decision(j, valid, τ_s, τ_c)`로 상태를 정한다. 근거 문단은 `sys_decision`이 돌려준 문단이다.
8. 문장마다 결과를 저장하고, 모두 종결되면 실행 상태를 정한다.

### 5.2 비주장 규칙

- **추천:** 다음 중 하나에 맞는 문장은 `not_claim`으로 두고 판정하지 않는다. 규칙은 코드 상수로 두고 `policy_version`에 포함한다.
  - 물음표로 끝나는 문장
  - "문단에", "제공된 정보", "확인할 수 없", "알 수 없", "언급되어 있지 않", "추가 정보가 필요" 같은 답변 불가·자료 언급 표현을 포함하는 문장
  - 숫자도 고유명사 후보(2자 이상 한글 명사 연속)도 없는 10자 미만 문장
  - 숫자가 없는 목록 머리말: "다음과 같습니다/다음과 같다/아래와 같습니다/아래와 같다"나 콜론(:)으로 끝나는 문장(로컬 실제 앱 확인 뒤 추가, 정책 `a2-provisional-2`)
- **근거:** 생성 프롬프트가 "문단에 없는 내용은 추측하지 마세요"라고 지시하므로(`generate.py:8-9`) 서비스 생성기는 "문단에서 확인할 수 없습니다" 같은 문장을 낸다. 이를 판정하면 "확인할 수 없다"는 문장에 ❔가 붙는 이상한 화면이 되고 호출만 쓴다. A-1 라벨 정의도 이런 문장을 "비주장"으로 평가에서 뺐다.
- **틀렸을 때 비용:** 실제 사실 문장이 비주장 표현을 포함하면 배지 없이 지나간다(재현율 손실). 6절 평가에서 규칙이 걸러 낸 문장 중 AI 라벨이 "주장"인 비율을 보고하고, 5%를 넘으면 해당 표현을 규칙에서 뺀다(사전등록 항목).

### 5.3 주장 수 상한

- **추천:** 실행당 판정 주장 상한 **8개**. 9번째 문장부터는 `unjudged`(사유 `claim_cap`)로 두고 화면에 "긴 답변의 뒷부분은 판정하지 않았습니다"를 띄운다.
- **근거:** 1B 생성기 최대 5개, 서비스 생성기는 더 길 수 있다(2.3). 생성 프롬프트가 3~5문장을 지시하므로 8개는 넉넉한 여유다. 상한은 실행당 토큰을 8 × 5,070 ≈ 40,600개 이하로 묶는다.
- **틀렸을 때 비용:** 상한을 넘는 답변이 잦으면 뒷문장이 늘 회색이 된다. 7.5절 지표 `evidence_claims_per_answer` p95가 7을 넘으면 생성 옵션 `num_predict`를 줄이는 쪽으로 대응한다(상한을 올리지 않는다).

## 6. 평가: 계층형 판정 검증과 ✅ 임계값 재설정 (사전등록)

두 질문을 **한 번의 새 데이터 수집**으로 답한다. A-1 홀드아웃은 다시 열지 않으며, A-1의 40개사는 표본에서 뺀다.

### 6.1 가설

| ID | 가설 | 채택 관문(확인 세트, 1회 실행) |
|---|---|---|
| H-prec | 조정 세트에서 정밀도 우선으로 고른 τ_s가 새 생성기 답변에서 ✅ 정밀도 0.90 이상을 낸다 | ✅ 정밀도 점추정 ≥ 0.90 이고 2단 군집 부트스트랩 95% 하한 ≥ 0.80 |
| H-low | 어휘 겹침이 θ_low 미만인 주장을 JEV 없이 ❔로 둬도 지지 주장을 거의 놓치지 않는다 | 하단 구간 주장 중 AI 라벨 지지됨 비율 ≤ 0.05 이고 하단 구간이 전체 주장의 20% 이상 |
| H-high | 어휘 겹침이 θ_high 이상이고 숫자 확인을 통과한 주장을 JEV 없이 ✅로 둬도 정밀도가 유지된다 | 상단 구간 정밀도 ≥ 0.95, 그리고 상단 구간을 적용한 전체 ✅ 정밀도가 SYS 단독 ✅ 정밀도보다 0.02 이상 낮지 않음. (2026-10-03 개정, A-2 데이터 전: 확인 세트 상단 구간 주장이 30개 미만이면 판정 불가 → 미채택. 조정 세트 ≥ 30 규칙과 일관) |
| H-tier (종합) | 채택된 구간을 합친 계층형 판정이 SYS 단독과 실용적으로 동등하면서 JEV 호출을 줄인다 | AUC 차이(계층형 − SYS) 95% 구간이 [−0.05, +0.05] 안이고 JEV 호출 감소율 ≥ 30% |

- **H-low와 H-high는 따로 채택한다.** 한쪽만 통과하면 그쪽 구간만 제품에 켠다. 둘 다 실패하면 제품은 모든 주장을 JEV로 판정한다(1차 필터 끔).
- **사전 예상:** H-high는 실패할 가능성이 높다. 주체 교체 문장은 어휘가 거의 같아 겹침이 높고, 어휘 겹침은 의역 대 주체 교체에서 AUC 0.639였다(2.3). 그래서 상단 구간은 숫자 확인 통과에 더해 **주장의 회사명 후보가 문단에 그대로 있을 것**을 조건으로 붙여 시험한다. 그래도 실패하면 H-low만 쓴다. 이 예상을 사전등록 파일에 적어 사후 해석을 막는다.

### 6.3 임계값 선택 규칙 (조정 세트)

**✅ 임계값 τ_s (정밀도 우선):**

1. τ_c는 A-1 값 **0.35로 고정**한다. 반박 오탐률(홀드아웃 0.014)이 이미 낮고, 조정 대상을 줄여야 확인 세트 하나로 결론을 낼 수 있다.
2. 후보는 **0.55~0.95, 0.05 간격**이다. 0.50 이하는 후보에서 뺀다. Stage 0 반복 일관성 경계 사례(지지 확률 0.43~0.54에서 판정이 오감)와 Stage 1 주체 교체 오판정이 모두 그 구간에 있었다.
3. 조정 세트 ✅ 정밀도 **≥ 0.93**인 후보 중 가장 작은 값을 고른다. 목표 0.90보다 0.03 높이는 이유는 A-1에서 조정 0.90 → 확인 0.797 → 홀드아웃 0.807로 줄어든 폭을 미리 반영하기 위해서다.
4. 조건을 만족하는 후보 중 조정 세트 ✅가 30개 미만인 값은 버린다(정밀도 추정이 불안정).
5. 없으면 **0.85**로 둔다.
6. 결과와 함께 τ_s ± 0.05 구간에 지지 확률이 걸린 주장 비율(경계 비율)을 보고한다.

**1차 필터 θ_low·θ_high:**

1. 후보는 `lex_score` 0.05~0.95, 0.05 간격이다.
2. θ_low: 하단 구간(`lex < θ_low`)의 AI 라벨 지지됨 비율이 0.03 이하인 후보 중 가장 큰 값.
3. θ_high: 상단 구간(`lex ≥ θ_high` 이고 숫자 확인 통과, 회사명 조건 통과)의 AI 라벨 정밀도가 0.97 이상인 후보 중 가장 작은 값. 상단 구간 주장이 30개 미만이면 θ_high 없음.
4. 조정 기준(0.03, 0.97)을 확인 관문(0.05, 0.95)보다 엄격하게 둬 축소 여유를 둔다.

**MCA 2.3(b) 경계:** θ와 τ_s는 **AI 참조 라벨**로만 고른다. JEV 출력을 정답으로 삼아 θ를 맞추는 것(예: "JEV가 지지한 주장을 어휘 겹침으로 재현하는 구간")은 JEV 출력을 흉내 내는 분류기를 만드는 일이므로 하지 않는다. 1차 필터는 JEV 출력으로 학습한 모델이 아니라 라벨 기준으로 구간을 정한 규칙이다. 이 원칙을 사전등록 파일에 적는다.

### 6.4 사전등록과 실행 순서

1. **사전등록 파일** `lab/evidence/prereg_a2.json`을 새로 만든다(기존 `prereg*.json`은 고치지 않는다). 담는 것: 6.1 가설·관문, 6.2 추첨·분할 규칙과 시드, 6.3 선택 규칙, 비주장 규칙 문구, 생성기 태그·digest, 판정 질문 해시(`judge.QUESTION_SHA`), `lex_score` 코드 해시, 부트스트랩 설정(2단 군집, 2,000회, 시드 20261103), 중지 조건, 예산 상한(입력 토큰 6,000,000).
2. 변경은 기존 원장 `lab/evidence/attempts.jsonl`에 `"study": "a2"` 표시로 이유와 함께 덧붙인다(기존 줄은 고치지 않는다).
3. 추첨·분할 → `lab/evidence/split_a2.json` 커밋(JEV 호출 전).
4. 조정 세트 질문·답변·주장·라벨 → τ_s·θ 선택 → `lab/evidence/results/a2-tune.json`.
5. 확인 세트 질문·답변·주장·라벨을 **JEV 호출 전에** 끝내고 동결 파일 `lab/evidence/prereg_a2_check.json`(해시 묶음, A-1 동결 파일과 같은 항목)을 커밋한다.
6. 확인 세트에서 SYS 단독과 계층형을 **한 번** 실행 → `lab/evidence/results/a2-check.json` → 리포트 `docs/lab/evidence-a2-report.md`.
7. **확인 세트 ✅ 예측이 150개 미만이면** 주결과를 기술 통계로만 보고하고, 제품은 H-prec 실패와 같은 규칙(아래)을 따른다.

**관문 결과가 제품에 반영되는 규칙(미리 정함):**

| 결과 | 제품 정책 `a2-v1` |
|---|---|
| H-prec 통과 | 조정 세트에서 고른 τ_s |
| H-prec 실패 | τ_s **0.85** 고정. 리포트에 "정밀도 목표 미확인"을 적고, 배지 툴팁에 "확신도 기준을 보수적으로 둔 시험 운영"을 덧붙인다 |
| H-low 통과 | 하단 구간 켬(θ_low) |
| H-high 통과 | 상단 구간 켬(θ_high) |
| 둘 다 실패 | 1차 필터 끔, 전부 JEV |

- 확인 세트 결과를 보고 τ_s·θ를 다시 고르지 않는다. 다시 고르려면 새 데이터로 새 사전등록을 한다.
- **평가가 끝나기 전 제품 정책:** `a2-provisional` — τ_s **0.70**, τ_c 0.35, 1차 필터 끔. 0.70은 경계 구간(0.43~0.54)에서 충분히 떨어진 값이다. 이 정책으로 판정한 실행은 요약줄에 "(시험 기준)"을 붙인다. `a2-v1`이 정해지면 기존 실행은 그대로 두고, 사용자가 연 스레드에서만 `rejudge` 실행을 만들 수 있다(자동 일괄 재판정은 하지 않는다 — 호출 한도를 소모하므로).
- **틀렸을 때 비용:** 잠정 τ_s 0.70이 너무 높으면 ✅가 적어(재현율 손실) 기능이 인색해 보이고, 낮으면 틀린 ✅가 나간다. 정밀도 우선 원칙상 앞쪽 비용을 택한다. 평가 한 번(로컬 반나절 분량 호출)으로 바로잡힌다.

### 6.5 생성기를 바꿀 때 다시 재는 절차

정책은 (JEV 모델, 생성기 태그·digest, 판정 질문 해시, 비주장 규칙) 묶음에 묶인다. 이 중 하나라도 바뀌면:

1. 바뀐 묶음을 새 `policy_version`으로 만들고, 그 전까지 제품은 직전 정책으로 판정하되 요약줄에 "(시험 기준)"을 붙인다.
2. 6.2~6.4와 같은 절차를 **새 무작위 40개사**(직전 연구들의 기업 모두 제외, 시드는 6.2절처럼 사전등록 파일에 미리 적는 임의 상수)로 다시 한다. 이전 확인 세트는 재사용하지 않는다.
3. 같은 비교를 보고한다: SYS 단독 대 어휘 겹침 기준선 AUC 차이(A-1 주결과와 같은 형식), ✅ 운영점, 계층형 관문, 통제 주장 변형 유형별 정확도(특히 주체 교체), 비주장 규칙 오분류율.

|---|---|---|
| 질문 임베딩 + Qdrant 검색 | 500ms | 로컬 Ollama 임베딩 1회 + 필터 검색. 넘으면 지표만 남긴다 |
| 답변 생성 | 타임아웃 60초 | 측정값 없음. 6절 평가 중 생성 지연 p50/p95를 함께 기록해 리포트에 싣고, p95의 2배로 타임아웃을 다시 정한다. 초과 시 504와 "답변 생성 시간이 초과되었습니다"(기존 `chat.py:141-142`와 같은 문구) |
| 저장 + 판정 작업 시작 | 200ms | DB 행 2개 커밋 + `asyncio` 작업 생성 |
| 작업 시작 지연(커밋 → 실행기 첫 줄) | 500ms | 같은 이벤트 루프 안이라 보통 수 ms. 넘으면 결정 4-1의 이전 조건 ② |
| 주장 1개 JEV 호출 | 시도당 타임아웃 **2초**, 재시도 1회 | 묶음 p99 최대 583ms의 약 3.4배. 단건 p95 519ms는 쓰지 않는다(묶음만 쓴다). A-1 `TIMEOUT_S` 10초는 평가용이라 제품에서는 너무 길다 |
| 판정 실행 전체 | 목표 p95 **1.5초**, 마감 **8초** | 주장 p95 5개 ÷ 동시성 3 = 2묶음 × 호출 p95 401ms ≈ 0.8초 + 로컬 계산·저장. 마감은 "한 주장이 첫 시도 2초 + 재시도 2초를 다 쓰고, 두 번째 묶음도 그럴 때"를 덮는 값이다. 마감에 걸린 주장은 `unjudged`(사유 `deadline`) |
| 프런트 폴링 | 500ms 간격, 15초 상한 | 결정 4-1 |

- **동시성 3의 근거:** 주장 p95 5개를 두 묶음에 끝낸다. 5로 올리면 한 묶음이지만 TypeSafe 쪽 동시 요청 제한을 아직 재지 않았다. 3은 평가 중 순차 호출(동시성 1)에서 한 단계 올린 보수적 값이다. 7.5절 지표에서 HTTP 429가 0이고 p95가 목표를 넘으면 4로 올린다.
- **틀렸을 때 비용:** 2초 타임아웃이 짧으면 드문 지연이 `unjudged`로 바뀐다. 첫 시도 1,462건 중 실패 0건, p99 583ms라 2초를 넘는 호출은 드물 것으로 본다. 지표 `evidence_jev_timeouts`가 하루 1%를 넘으면 3초로 올린다.

### 7.2 일일 호출·토큰 상한과 초과 시 동작

호출 수와 입력 토큰 수로만 정한다(금액은 쓰지 않는다, A-1 spec 9절 14.1).

| 상한 | 값 | 산출 |
|---|---|---|
| 사용자별 일일 JEV 호출 | **150회** | 근거 모드 답변 약 40~50개(답변당 주장 p50 2~p95 5개, 캐시 적중 제외) |
| 사용자별 일일 입력 토큰 | **750,000** | 150회 × p95 5,070 ≈ 760,000에서 내림 |
| 전역 일일 입력 토큰 | **3,000,000** | 호출 약 590~660회. 포트폴리오 시연 규모(사용자 수 명)를 덮고, A-1 평가 전체 사용량(약 620만)의 절반 이하로 하루 최악 소모를 묶는다 |
| 실행당 | 주장 8개(5.3절) ≈ 40,600 토큰 | |

- **세는 법:** Redis 키 `evidence:quota:{YYYYMMDD}:global:tokens`, `evidence:quota:{YYYYMMDD}:user:{id}:calls`, `…:tokens`, 만료 48시간. 날짜는 KST 기준. 두 단계만 한다: ① 실행 시작 전에 사용자·전역 잔여가 실행 예상치(판정할 주장 수 × 5,070) 이상인지 확인한다. ② 호출이 끝날 때마다 응답의 실제 `usage.input_tokens`와 호출 1회를 `INCRBY`로 더한다. 예약·정산은 하지 않는다. 카운터가 Redis에 있으므로 재시작해도 남고, 나중에 프로세스가 늘어도 같은 값을 본다(2.2절 `JevClient` 한계 해소).
- **초과 폭:** 확인은 실행 시작 때 한 번이므로 한도를 넘는 폭은 실행 1건(주장 8개 ≈ 40,600 토큰) 이내로 묶인다. 사용자별로는 진행 중 실행을 1건으로 제한해(진행 중이면 새 실행은 앞 실행이 끝난 뒤 시작) 이 경계를 지킨다. 전역 한도는 서로 다른 사용자의 실행이 동시에 시작하면 그 수 × 40,600까지 넘을 수 있고, 포트폴리오 규모에서는 이를 받아들인다.
- **캐시 적중은 한도에서 빼지 않는다**(호출이 없으므로).
- **초과 시 동작:**
  - 실행 시작 전에 사용자·전역 잔여가 실행 예상치(주장 수 × 5,070)보다 적으면 실행 전체를 `limited`로 끝낸다. 답변은 그대로 보인다(3.2절).
  - 다음 날 0시(KST)에 자동으로 풀린다. 관리자 해제 기능은 만들지 않는다.
- **평가 원장과 분리:** 제품 호출은 `lab/data/evidence/jev_calls.jsonl`에 쓰지 않는다. 평가 예산 상한(A-1 20,000,000, A-2 6,000,000)과 섞이지 않게 한다.
- **틀렸을 때 비용:** 상한이 너무 낮으면 시연 중 `limited`가 뜬다. 하루 사용량은 7.5절 지표로 보이므로 상한을 설정값(`EVIDENCE_DAILY_*`)으로 두고 재배포 없이 환경 변수로 조정한다.

### 7.3 장애 정책

| 상황 | 처리 | 화면 |
|---|---|---|
| 타임아웃(2초) | 같은 요청 1회 재시도 | 재시도도 실패하면 그 문장 ⊘ |
| HTTP 5xx, 연결 오류 | 1회 재시도 | 같음 |
| HTTP 429 | 재시도하지 않는다. 실행의 남은 주장을 `unjudged` | 실행 `partial` 또는 `failed`, "잠시 후 다시 판정" |
| HTTP 401·403 | 재시도하지 않는다. 실행 `failed`(`http_4xx`), 오류 로그 1회 | `failed` 화면, `다시 판정` 버튼 숨김 |
| 응답 검증 실패(모델 불일치, 선택지 누락, 확률 범위·합 오류 — `parse_answers`) | 1회 재시도(A-1과 같음) | 실패 시 ⊘ |
| 실행 마감 8초 초과 | 남은 주장 `unjudged`(`deadline`) | `partial` |
| 앱 재시작·프로세스 종료 | 진행 중 실행은 시작 시 `failed`(`stale`)로 바뀐다(결정 4-1). 자동 재실행 없음 | `failed`, `다시 판정` 버튼 |
| Redis 장애 | 한도를 셀 수 없으므로 **판정하지 않는다**(실행 `failed`, `quota_unavailable`) | `failed` |
| API 키 없음 | 근거 모드 토글 자체를 숨긴다(앱 시작 시 키 존재만 확인, 값은 읽어 두지 않음) | 토글 없음 |

- 재시도는 **1회**만 한다(A-1 `JevClient`와 같음). 재시도 간 지연은 두지 않는다. 마감 8초 안에서 지연을 두면 두 번째 묶음이 마감에 걸린다.
- **실패한 판정을 ❔로 보이지 않는다.** 장애는 언제나 ⊘다(3.2절).
- **`pending`으로 남은 실행 정리:** 생성 후 60초가 지난 `pending`·`running` 실행은 조회 시 `failed`(`stale`)로 바꾼다.
- **틀렸을 때 비용:** Redis 장애에 판정을 끄면 Redis가 죽은 동안 기능이 멈춘다. 한도 없이 호출하는 쪽의 비용(무제한 소모)이 더 크다고 판단했다.

### 7.4 캐시

- **추천:** 성공 응답만 Redis에 캐시한다. 키 `evidence:jev:{request_key}`(`jev.request_key` 그대로 — 모델·state·질문 해시), 값은 검증된 확률 분포, TTL **30일**.
- **근거:**
  - 같은 질문·같은 회사면 검색 문단 8개와 생성 답변이 같아진다(`temperature 0`, 고정 seed). 같은 주장·문단이면 같은 요청 키라 호출 없이 같은 판정을 돌려준다.
  - 캐시는 경계선 사례의 반복 흔들림(Stage 0: 50건 중 3건)을 사용자 화면에서 없앤다. 같은 답변에 다시 판정할 때 배지가 바뀌지 않는다.
  - 문단이 바뀌면 state가 바뀌어 키도 바뀌므로, 정정·재적재된 문단에는 자동으로 새 판정이 나간다.
- **`retry` 실행은 캐시를 쓴다**(실패는 캐시하지 않으므로 실패한 주장만 새로 호출된다). `rejudge`(임계값 변경)는 확률을 다시 받을 필요가 없으므로 저장된 `s`, `c`로 SYS 규칙만 다시 적용하고 **호출하지 않는다**. 저장된 확률이 없는 주장(`lex_low`·`lex_high` 경로)은 새 정책의 θ에서도 같은 구간이면 그 판정을 유지하고, 구간을 벗어나면 `unjudged`(사유 `needs_call`)로 둔다. 이런 주장은 사용자가 `다시 판정`을 누를 때만 호출한다.
- 캐시 값은 JEV 출력이다. 캐시를 학습·분석용 데이터로 내보내지 않는다(MCA 2.3(b)).
- **틀렸을 때 비용:** JEV 모델이 바뀌면 캐시가 무효다. 키에 모델명이 들어가므로 자동으로 갈린다.

### 7.5 관측

**로그:** 판정 실행 하나에 구조화 로그(JSON) 한 줄, JEV 시도마다 한 줄.

- 실행 로그: `run_id`, `chat_id`, `policy_version`, `status`, `error_code`, `claims`(전체·비주장·`lex_low`·`lex_high`·`jev`·`unjudged` 개수), `calls`, `cache_hits`, `input_tokens`, `start_delay_ms`, `duration_ms`.
- 시도 로그: `run_id`, `claim_idx`, `request_key` 앞 12자, `attempt`, `ok`, `http_status`, `latency_ms`, `input_tokens`, `error`(200자).
- **남기지 않는 것:** state 원문, 주장 원문, 문단 본문, 사용자 질문, API 키, 사용자 이메일. 원문이 필요하면 DB 판정 기록(소유자 권한)에서 본다.

**지표:** 저장소에 지표 수집 구성이 없으므로(2.1) 새 수집기를 들이지 않고, 판정 기록 테이블에서 계산하는 관리자 조회 `GET /api/admin/evidence/stats?days=7`을 둔다(기존 `app/routes/admin.py`에 추가, 관리자 권한).

| 지표 | 경보 기준(관리자 화면 빨간 표시) |
|---|---|
| `evidence_run_duration_ms` p50/p95 | p95 > 1.5초 |
| `evidence_start_delay_ms`(작업 시작 지연) p95 | > 500ms |
| `evidence_jev_latency_ms` p50/p95/p99(첫 시도) | p95 > 600ms |
| `evidence_jev_failure_rate`(첫 시도 기준), 재시도 성공률 | > 1% |
| `evidence_jev_timeouts`, HTTP 429 수 | 타임아웃 > 1%, 429 > 0 |
| 상태 분포(`done`/`partial`/`failed`/`limited`/`skipped`) | `failed`+`partial` > 5% |
| 판정 분포(✅/⚠️/❔/⊘/비주장) | ⊘ > 5% |
| 경로 분포(`lex_low`/`lex_high`/`jev`) | — |
| `evidence_claims_per_answer` p50/p95 | p95 > 7(5.3절) |
| 일일 호출·입력 토큰(사용자별 상위 5, 전역) | 전역 > 상한의 80% |
| 캐시 적중률 | — |

- **틀렸을 때 비용:** DB 집계는 행이 많아지면 느려진다. 포트폴리오 규모(하루 수백 실행)에서는 문제없고, 조회 기간을 최대 30일로 막는다.

## 8. 외부 전송 고지 (MCA 4 — A-1에서 넘어온 항목)

- **보내는 것:** 회사명, AI 답변 문장(주장), 공시 문단 8개. **사용자 질문 원문은 보내지 않는다**(`judge.build_state`에 질문이 없다).
- **남는 위험:** 생성 답변이 질문 내용을 되풀이할 수 있다.
- **추천:**
  1. 모드를 처음 켤 때 한 번, 그리고 토글 옆 도움말에 상시: "근거 판정을 위해 AI 답변 문장과 공시 문단을 외부 판정 서비스(TypeSafe JEV)로 보냅니다. 질문 원문은 보내지 않습니다. 개인정보를 질문에 넣지 마세요." 처음 고지는 확인 버튼을 눌러야 모드가 켜지고, 확인 사실을 사용자 상태(Redis `user_state`)에 남긴다.
  2. 전송 전 답변에서 이메일, 휴대전화 번호, 주민등록번호 형태를 정규식으로 찾으면 실행 전체를 `skipped`(`pii`)로 끝낸다. 판정 대상 답변은 공시 문단만 보고 쓴 것이라 정상 답변에 이런 패턴이 나올 일이 거의 없다.
  3. 기존 가드레일 `check_guardrails`(`app/lib/guardrails.py:20`)를 질문에 먼저 적용한다(에이전트 경로와 같음).
- **틀렸을 때 비용:** 고지 확인이 한 번 더 클릭을 요구한다. 정규식 오탐(공시 문단의 전화번호 등)이면 판정이 생략된다. 오탐은 `skipped` 지표로 보이므로 패턴을 좁힌다.

## 9. 테스트 (단위, 외부 호출 없음)

CLAUDE.md 규칙대로 기능마다 실패하는 테스트를 먼저 쓴다. 모두 가짜 JEV 응답·가짜 임베딩·가짜 Redis(`fakeredis` 또는 메모리 대체)로 돈다.

- `claim_spans`: 결과 문장이 `split_sentences`와 같고, 오프셋으로 잘라낸 원문이 문장과 같다(글머리표 제거 포함).
- 비주장 규칙: 각 표현, 물음표, 짧은 문장 경계.
- `lexical.lex_score`: `lab/evidence/baselines.lex_score`와 고정 예제 20개에서 같은 값(테스트에서만 `lab`을 import).
- `ServiceJevClient`: 캐시 적중 시 호출 없음, 실패는 캐시하지 않음, 타임아웃 → 재시도 1회, 429·401 재시도 없음, 응답 검증 실패 → 재시도, 요청 키가 `jev.request_key`와 같음.
- 한도: 실행 전 잔여 확인 → `limited`, 호출 뒤 실제 토큰 `INCRBY`, 사용자당 진행 중 실행 1건, KST 날짜 경계, Redis 장애 시 `failed`.
- 백그라운드 작업: 시작 시 `pending`·`running` → `failed`(`stale`), 60초 지난 실행 조회 시 `stale`, 작업 예외가 실행을 `failed`로 남김(조용히 사라지지 않음).
- 실행기: 동시성 상한 준수, 마감 시 `unjudged`, 주장 상한 8, `sys_decision` 결과 매핑, 계층형 경로(`lex_low`/`lex_high`/`jev`) 분기, `rejudge`가 호출 없이 저장 확률로 다시 판정.
- 저장: 스레드 삭제 시 판정 행 cascade(SQL `DELETE` 경로), 소유자 아닌 사용자의 실행 조회 404.
- 개인정보 패턴: 탐지·비탐지 예.
- 기존 근거 판정 테스트(`tests/evidence`)는 그대로 통과해야 한다(CLAUDE.md의 명령).
